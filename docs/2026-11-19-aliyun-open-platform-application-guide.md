## 0. 先行结论（最短版）

**这是「开发者一次性申请」，不是「AFM 每个使用者都要申请」。**

| 角色 | 要做什么 | 要拿到什么 |
|---|---|---|
| 开发者（你，发布 AFM 的人） | 到阿里云盘开放平台注册**一个应用** | `client_id`（必填）、`client_secret`（可选，见 §3） |
| AFM 普通使用者 | **什么都不用申请** | 只在自己机器上点「授权」→ 用阿里云盘账号登录 |

类比：AFM 接百度网盘时，用户不需要去百度申请 AppKey；百度网盘的 cookie 由用户自己的账号产生。
阿里云盘不一样的地方在于它走**官方 OAuth**，授权页必须带一个 `client_id` 才打得开 —— 这个 `client_id` 是**应用的身份**，不是用户的身份。

### ⚠️ 但当前实现是「自测/自用过渡态」

现在代码里 `client_id` / `client_secret` / `redirect_uri` 是**连接表单上的三个输入框**（`src/modules/settings/ui/categories/remote/connection-form.vue`），谁用谁填。
这意味着现在**每个 AFM 使用者都得以「开发者」身份自己去申请一个应用**——这显然不是发布形态。

正确的发布形态是：`client_id` 内置进 AFM（编译期或首启配置），用户在 UI 上**只看到一个「授权」按钮**，点一下拉授权页、登录、回来就完事。

⇒ 换句话说：**「要不要每个使用者都申请」这个问题的答案，取决于你要不要正式发布。**
只给自己用 → 你申请一次就够，自己填表单。
要发布给别人用 → 你申请一次，把 `client_id` 内置，用户零申请。**永远不需要用户申请。**

> 这张表单三字段的存在意义是**自测期不把开发者的应用密钥写进仓库**，它是过渡态，不是产品设计。正式发布前必须收掉（或改成「高级选项」折叠起来）。

## 1. 为什么阿里云盘不能像百度/夸克那样扫个码就完事

AFM 里百度、夸克走的是**内嵌 WebView2 + cookie 轮询**（`src-tauri/src/baidu_login.rs`、`quark_login.rs`）：
开一个 WebView 指向网盘网页 → 用户在网页里正常登录 → 后端读 cookie，读到 `BDUSS`（百度）/ `__pus`（夸克）就认领。
**没有任何应用身份参与**，所以用户不需要申请任何东西。

阿里云盘**技术上也能这么干，但代价完全不同**，见 §6.2。当前选的是官方 OAuth，所以多了「应用」这个概念。

## 2. 申请前置条件（先自检，不然白跑）

按顺序过，任意一条不满足就先去解决，别急着注册：

1. **阿里云账号**已完成**实名认证**（个人或企业都行，实名是硬门槛）。
2. **阿里云盘账号**本身可用（能正常登录网页版 `https://www.alipan.com/`）。
3. **资质**：开放平台创建应用通常要求「开发者资质」。个人资质这条路**当前存疑**（见 §4），企业资质基本无碍。
4. 手上有一个**能被本机监听的回调地址**。AFM 已给默认值：`http://127.0.0.1:47832/callback`（**留空即用这个**，不用你操心）。

## 3. 申请全流程

> 本节步骤为**流程骨架**。控制台的按钮名、菜单层级、审核时长**本轮未联网复核**（见 §7），
> 以你实际看到的界面为准；若某步与本文件描述不同，**以控制台为准**，并回来更新本文件。

### 步骤 1 · 找到开放平台入口

阿里云盘开放平台的入口历史上换过几次域名，常见候选（**均未联网复核，逐个试**）：

- `https://www.alipan.com/developer`
- `https://openapi.alipan.com/`
- 阿里云盘官网页脚的「开放平台 / 开发者」链接
- 语雀上的官方文档站点（正文需登录，登录后通常带「控制台」跳转）

判据：打开的页面里出现**「创建应用」/「我的应用」**，就对了。

### 步骤 2 · 注册为开发者

首次进入需要同意开发者协议 + 填开发者信息（个人 or 企业主体）。
**这一步就是 §4 的资质卡点所在**，可能直接被拦。

### 步骤 3 · 创建应用

需要填/选的信息，逐项对应 AFM 的需求：

| 控制台字段 | AFM 需要填什么 | 说明 |
|---|---|---|
| 应用名称 | `Alpha File Manager`（或任意） | 会显示在用户的授权页上，属于**用户可见文案**，正式发布别写测试名 |
| 应用类型 | 选**「第三方应用」/「Web 应用」**一类（不是「自有应用」） | 因为授权发生在用户自己的机器上 |
| 回调地址 / `redirect_uri` | `http://127.0.0.1:47832/callback` | **必须与 AFM 实际用的完全一致**；AFM 留空时用的就是它 |
| 权限范围 / `scope` | `user:base` + `file:all:read` | 只读所需**最小集**；不要多申请写权限，审核更容易过，也少一层风险 |
| 应用图标、简介 | 可填则填 | 影响授权页观感，不影响功能 |

> **回调地址的坑**：`127.0.0.1` 这类回环地址在部分 OAuth 服务里必须显式登记才被接受；
> 阿里云盘控制台是否强制校验、允许多少个回调、是否允许 `http`（非 https），**未复核**。
> 如果控制台不接受 `127.0.0.1`，AFM 也支持填**任意**回调地址 —— 它的 code 捕获逻辑是
> 「拦截任意带 `code=` 的导航」，所以 `https://你有域名/callback` 一样能用（那个域名不需要真的部署东西）。

### 步骤 4 · 提交审核

提交后进入审核。**审核时长未复核**（社区说法从「几小时」到「数个工作日」不等，本轮无法验证）。

审核期间可以先把 `client_id` 拿到手 —— 多数平台在提交后就能看到 `client_id`，只是**未审核通过前授权页会拒绝**。
所以：拿到 `client_id` 不等于能用，**要等审核通过**。

### 步骤 5 · 取回凭据

审核通过后，在应用详情页拿两样东西：

- **`client_id`**：应用的公开身份。**必填**。可以展示、可以进前端、不算密钥。
- **`client_secret`**：应用的密钥。**可留空**！（见下）

#### 关于 `client_secret`：可以不要

AFM 的实现支持两种客户端模式（契约 §3）：

| 模式 | 你怎么填 | 后端行为 |
|---|---|---|
| **PKCE 公开客户端** | `client_secret` **留空** | 用 `code_verifier` + `SHA256` 生成 `code_challenge`（S256）走 PKCE，换 token 时不带 secret |
| 机密客户端 | 填 `client_secret` | 换 token 时带上 secret |

**推荐留空走 PKCE。** 理由：

1. 桌面应用的 `client_secret` 天然藏不住（二进制里能扒出来），挂个「机密」的名头只是自我安慰；
2. `client_secret` 一旦填进来就会跟着 DPAPI 密文走（`remote-credentials.json`），多一份要保管的东西；
3. 只有 `client_id` 时，就算泄露也只是一个公开标识，不构成凭据泄露。

> 例外：如果控制台**强制**要求 secret（有的平台不允许创建公开客户端），那就填。
> 代码会按「secret 非空 ⇒ 机密客户端」处理，两条路都通。

## 4. ⚠️ 最大的风险：个人开发者资质可能已经关了

### 已知情况

社区多源说法：**2025-07 之后阿里云盘暂停个人开发者应用申请，只接受企业资质**。

**这条本轮没有从官方文档确认**（`web_search` 不可用，语雀官方文档正文需登录）。
契约文档 §1.7 已把它登记为「未判定项」，这里延续同样口径：**既不当真，也不当假**。

### 怎么自己判别（5 分钟，比问任何人快）

按这个顺序试，**第一个能走通的层级就是你的实际处境**：

1. 打开开放平台 → 点「创建应用」。
   - **能进创建表单** ⇒ 个人资质至少没被完全封死，继续填。
   - **提示需要企业认证 / 资质不足** ⇒ 走第 2 步。
2. 看「开发者认证」页是否提供**个人**认证入口。
   - **有** ⇒ 认证完再回来创建。
   - **没有 / 灰掉 / 提示仅企业** ⇒ 个人这条路当前关闭。
3. 若确实关闭，只有三条出路（见 §5）。

**别做的事**：不要为了绕过资质去「借」别人的企业主体注册应用 —— 应用的责任主体和账号绑定，
后续出问题（用户数据、投诉、封禁）你无法处理，代价远大于收益。

## 6. Plan C 评估：改成扫码登录到底值不值

### 6.1 用户的原始条件

> 「如果步骤繁琐，则把阿里云的支持方式，修改为和百度网盘一致的扫码登录方式。」

**判定：当前不触发。**

「繁琐」的判据应该是**投入产出比**，不是**步骤条数**。逐条对比：

| | OAuth 申请路线 | cookie 扫码改造路线 |
|---|---|---|
| 一次性投入 | 填一个表单（10–20 分钟）+ 等审核 | 新写 `aliyun_login.rs` + 网页 API 适配层（预估 2–3 天） |
| 需要外部审批 | 是（资质审核） | 否 |
| 成功前提 | 能拿到 `client_id` | 阿里云盘网页接口可被程序调用 |
| 长期稳定性 | **官方契约，改版不影响** | **随前端改版随时失效** |
| 账号风险 | 无（标准 OAuth 授权） | 有（非官方接口，可能触发风控/条款风险） |
| 维护成本 | 近零 | 每次阿里云盘前端改动都要跟 |

⇒ **「步骤繁琐」这个触发条件不成立**：申请路线是 20 分钟的事，改造路线是几天 + 长期维护。
真正会触发 Plan C 的是**「资质拿不到」**（§4），那是**能不能**的问题，不是**繁不繁琐**的问题。

### 6.2 为什么 cookie 路线在阿里云盘上比百度/夸克难得多

百度、夸克能低成本走 cookie 路线，是因为它们的网页接口**请求签名简单或没有**，cookie 也相对长寿。
阿里云盘不是：

1. **请求签名**：阿里云盘网页端接口普遍带 `x-signature` 一类的签名头，算法随前端 bundle 走，**每次改版都可能变**。
   要复刻就得逆向前端 JS，且要长期跟。
2. **cookie 寿命短**：阿里云盘的会话 cookie 有效期明显短于百度 `BDUSS`，需要更频繁地重新扫码 / 静默续期，
   而续期本身又依赖签名 —— 一处断，整条链断。
3. **风控与条款**：非官方接口的自动化调用属于对方条款里通常受限的行为，账号被限流/封禁的风险不能忽略，
   **且这个风险落在用户身上，不是落在你身上** —— 这是最不该忽视的一点。
4. **只读也没用**：即便只做「列目录 + 读文件」，也绕不开签名和 cookie 续期这两件事。

⇒ Plan C 的结论是：**技术上可做，但不是「照抄百度那套」就能落地**，实质是一次小型逆向工程 + 长期维护承诺。
只有在 §4 确实走不通、且阿里云盘是刚需时，才值得启动。

## 7. 拿到 `client_id` 之后：在 AFM 里怎么用

### 7.1 现在（自测态）

1. 设置 → 远程 → 添加连接 → 协议选 **`aliyun_pan`**；
2. 表单里出现三个输入框：
   - **应用 ID**（`client_id`）：**必填**。空着点「登录」会被前端直接拦下（不发请求，避免一个必然失败的窗口）；
   - **应用密钥**（`client_secret`）：**建议留空**（走 PKCE，见 §3）；
   - **回调地址**（`redirect_uri`）：**建议留空**（后端默认 `http://127.0.0.1:47832/callback`，须与控制台登记值一致）；
3. 点「授权登录」→ 弹出内嵌授权窗（窗口 label `afm-aliyun-login`）→ 用阿里云盘账号登录并同意授权；
4. 授权完成后窗口自动关闭，表单状态变成「已登录」。

### 7.2 关键实现事实（用于排障）

| 项 | 值 |
|---|---|
| 授权页 | `GET https://openapi.alipan.com/oauth/authorize` |
| 换 token | `POST https://openapi.alipan.com/oauth/access_token`（form-urlencoded，`grant_type=authorization_code` / `refresh_token`） |
| scope | `user:base` + `file:all:read` |
| code 捕获 | 双保险：`WebviewBuilder::on_navigation` 命中 `code=` 即拦截 + `window.eval` 每秒轮询 `location.href` |
| 事件频道 | `afm://aliyun-login`（`waiting` / `ready` / `closed` / `timeout` / `error`） |
| 凭据落盘 | `remote-credentials.json`（DPAPI 加密），键 = 连接 id |
| 三参数不落连接表 | `client_id` / `client_secret` / `redirect_uri` 只活在表单态，登录成功后随会话进密文 |

### 7.3 正式发布前必须做的一件事

把 `client_id` **内置**进 AFM，表单里那三个输入框收进「高级选项」或直接删掉。
否则每个用户都得自己去申请一个应用 —— 这在产品上说不通（见 §0）。
