## 四、环境：坏掉的工具链与可用替代

### 4.1 Rust stable toolchain 损坏（沿用 2.2.1 handoff）

`rustup` 的代理 shim 从 `C:\Users\Duanyi\.cargo\bin` 消失，
且 `stable`(1.97.1) 的标准库只剩元数据存根。**可用替代**：

```powershell
$tc = 'C:\Users\Duanyi\.rustup\toolchains\1.90.0-x86_64-pc-windows-msvc\bin'
[Environment]::SetEnvironmentVariable('PATH', "$tc;$env:PATH", 'Process')
& "$tc\cargo.exe" test --lib
```

PATH 注入必须用 `[Environment]::SetEnvironmentVariable(..., 'Process')`，不要用 `$env:PATH`。

### 4.2 PowerShell 5.1 执行的中文脚本必须带 UTF-8 BOM（沿用）

无 BOM 的 `.ps1` 按 GBK 解析，中文乱码里的引号会破坏语法，**报错行号还和真实问题对不上**。
写完先自检（详见 `mcode-rules` 规则 O）。

### 4.3 Cargo 全局缓存 DB 损坏（新增 3.0.2 期间观察）

3.0.2 构建报 `warning: failed to save last-use data ... file is not a database`，
**但不影响构建**（cargo 1.90 用 SQLite 存 last-use，DB 损坏时只丢自动清理能力，编译继续）。
若升级 cargo 仍未自愈，可执行 `cargo clean` 或重建 `$CARGO_HOME/registry/cache` 子树。

```powershell
# 4. 生成带构建信息的 release 说明 + 创建/更新 GitHub 兜底 release

npm run release:github

# 5. 公网回读
npm run release:verify
```

### 3.0.2 期间踩到的发版坑（memory 规则 P 已沉淀）

- **构建前必须关掉所有 `target\release\alpha-file-manager.exe` 实例**。
  占用时报 `os error 5`（拒绝访问），失败点在最后一步，前面的几分钟全白等
- **重跑失败的 `prepare` 必须 `--bump none`**。不带 `--bump` 会默认 `patch`，把版本号推高到下一版
- **`--bump none` 会丢上一版的 `history[]` 归档**。`release:verify` 全绿查不出来
  （只比版本号/大小/sha256）。修法：`upload` 之前从**线上** `version.json` 取回上一版条目
  插回 `history[0]`

## 八、工作方式约定

- **面向用户的输出一律简体中文**（含代码注释里给人看的部分）。
- **不要在用户重启应用/服务的窗口期部署。**
- **验证必须测被测对象真实走的那条链路**；判别性结论要带对照组，
  不能拿「编译通过 / 退出码 0」当验证。
- 门禁要长在部署路径上，不能是旁边的可选步骤。
- 抓不到二进制、拆不动包、读不了源码时，**如实说「不可知」，不要写成「已排除」**。
- **构造罕见形状做覆盖前，确认形状真的能让代码走到该分支**；
  探针转红后核对失败信息是否等于你担心的那种坏结果，**只红不算数**。
- **行为异常先归因「构建形态」再怀疑代码**：`tauri dev` 与 `tauri build` 的差异是
  本项目验收已知的真坑（见 §3.5）。
