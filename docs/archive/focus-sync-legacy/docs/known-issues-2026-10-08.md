## BUG-1 ★ 注入逃逸到非对话框窗口,并自动触发回车 —— ✅ 已修复(待验证)

**严重度:高(安全)** —— 它能向任意前台应用输入文本并触发回车键。
**修复时间**:2026-10-08 13:30

### 现象(用户直接观察,非日志推断)

> 在弹出窗口中,不仅地址栏会填入 sigma 激活的路径……甚至会扩展到其他非弹出窗口,
> 比如我们当前的会话,在切换过来后,刚才就自动填入了路径并且回车发送了

即:焦点切到聊天窗口后,路径被自动输入并**回车发送**。

### 推断的机理(尚未用日志直接证实)

```
T0  monitor 检测到前台 HWND 是 #32770 文件对话框 → 发出 DialogEvent::Opened
T0+ main 收到事件,开始 UIA 扫描 best_edit / best_button(实测耗时 ~300ms)
T0+200ms  用户切换到另一个应用(聊天窗口)→ 前台变了
T0+300ms  H1 执行 SendInput:Ctrl+L → 路径 → Enter
          ★ SendInput 永远发给「发送那一刻的前台窗口」,而不是对话框
```

**现有两道护栏为何没拦住:**

| 护栏 | 检查内容 | 为何漏掉 |
|---|---|---|
| 护栏 1 | 文件名框读回,判断路径是否落进了文件名框 | 焦点在**别的进程**时,对话框的文件名框根本没变 → 判定「安全」→ 放行 Enter |
| 护栏 2 | `GetGUIThreadInfo` 查前台线程的焦点控件 automation_id | 只查「焦点在不在 1001 文件名框」,**没有校验这个前台窗口是不是那个对话框** |

**缺失的检查**:SendInput 之前,必须确认**当前前台 HWND 仍等于目标对话框 HWND**,
而且必须**在发送的同一时刻**验证(而不是 300ms 前)。

### ✅ 修复内容(v0.5.7 BUG-1)

新增 `uia_inject.rs::dialog_still_foreground(state, dialog_hwnd)`,在**两个**
`SendInput` 调用点前**各校验一次**:

```
UIA 扫描 ~300ms
  ↓
[闸门 1] dialog_still_foreground?  ← 不通过则一个按键都不发,return false
  ↓
SendInput 批次1(Ctrl+L / End / Back×128 / 路径)
  ↓
80ms sleep + 两道原有护栏
  ↓
[闸门 2] dialog_still_foreground?  ← 不通过则跳过 Enter,return true
  ↓
SendInput 批次2(Enter)
```

校验内容两条,同时满足:
1. `IsWindow(hwnd)` —— 对话框没被销毁(句柄可能被复用)
2. `state.foreground_dialog() == hwnd` —— monitor 发布的值,每次轮询刷新(≤8ms 新鲜度)

**刻意不使用 `GetForegroundWindow()`**:本代码跑在无消息泵的 HTTP 线程上,
该调用返回过与 monitor 矛盾的值(见 F-1 记录)。

**返回值的语义选择**:
- 闸门 1 不过 → `return false` → 不发任何按键,交回 H2 回退
- 闸门 2 不过 → `return true` → 地址栏已填好,**不**落回 H2
  (否则会往用户已不再注视的对话框的文件名框里写东西)

**验证清单(修复后待确认)**:
- [ ] 在 Sigma FM 切目录后**立刻**切到聊天窗口 → 聊天窗口**不得**收到任何输入
- [ ] 日志出现 `ABORTING before dispatching any keys (BUG-1)` 或
      `SKIPPING Enter (BUG-1)` —— 说明闸门确实拦下了一次
- [ ] 地址栏导航仍然生效(不能为了修 BUG-1 把功能整体关掉)

## BUG-2 文件名框被写入「路径片段 + 原文件名」—— ✅ 已修复(根因已更正)

**严重度:高** —— 直接污染用户输入,且是 BUG-3 的成因。
**修复时间**:2026-10-08 15:20(v0.5.8,已部署)

### 现象(截图 + 日志双重证实)

日志 `spike.log`:
```
13:09:23  READ        hwnd=12521020 path='E:\办公文件\02 1号位\线上培训\第4次线上培训_2026-10-08'
13:09:23  SpIkeError: dialog path='E:\...\第4次线上培训_2026-10-08' current='E:\...'; writing current
13:09:23  UIA SetValue OK on automation_id='1001' name='文件名:' target='E:\...\第4次线上培训_2026-10-08'
13:09:52  READ        hwnd=12521020 path='线上培训\第4次线上培训纪要_2026-10-08'   ← 污染已存在
13:10:01  READ        hwnd=12521020 path='线上培训\第4次线上培训纪要_2026-10-08'
13:10:17 / 13:10:42 / 13:10:48 / 13:11:09  READ  同上（持续 77 秒，6 次）
```

截图文件名框内容:`线上培训\第4次线上培训纪要_2026-10-08`

### 读出来的信息

| 片段 | 来源 |
|---|---|
| `线上培训\` | **目标路径的尾部片段**(来自 `E:\办公文件\02 1号位\线上培训\...`) |
| `第4次线上培训纪要_2026-10-08` | **用户自己的原文件名**(目标路径里是 `第4次线上培训_2026-10-08`,没有「纪要」) |

⇒ 完整路径曾经整个进过文件名框(13:09:23 那条 READ 就是证据),之后只剩尾部片段。

### ✅ 根因(2026-10-08 全量日志统计更正)

原文推断是「H1 失败后回退 H2,H2 的第二次 SetValue 与对话框自身的输入处理竞争,
还原不完整」。**日志不支持这个说法:**

| 检验项 | 结果 |
|---|---|
| `UIA SetValue OK on automation_id='1001'`(F3 基线**唯一**的日志行) | **全历史仅 5 次** |
| 其中第 5 次的时刻 | **2026-10-08T05:09:23Z = 本地 13:09:23 —— 正是污染首次出现的那一条** |
| BUG-2 整个窗口(13:09–13:11)内 H1 的结果 | **每一次都 `H1 succeeded`** |
| BUG-2 窗口内 H2 的执行次数 | **0 次 —— H2 根本没跑** |
| H2 在全部历史中的最后一次执行 | 2026-10-07T07:24Z,在 F-1 前台修复让 H1 不再退化到它之前 |

⇒ **写脏文件名框的是 F3,不是 H2。**

### 为什么 F3 会被执行到

整个 H1 → H2 回退链的入口条件是 `is_winui3_wrapped`。而在**对话框刚打开后的第一次
注入**时,`FileNameControlHost` / `50003` 标记尚未出现在 UIA 树里 —— 于是
`has_filename_host = false`,包装检测失败,**H1/H2 整条链被跳过**,直接落到 F3。

也就是说:**F3 恰恰在对话框最不可靠的时候被执行**。同一窗口的 13:09:52 起
(对话框已完全成型),`WinUI 3 wrapped detected` 正常出现,走的就是 H1,地址栏正常。

### ✅ 修复内容(v0.5.8)

`uia_inject.rs` 的 F3 基线原本是:

```rust
value.SetValue(&BSTR::from(target_path))?;     // 写进去,就没有然后了
```

现在:

1. 写入**之前**快照文件名框当前值(用户自己的文件名,而不是我们刚写进去的东西)
2. 写入 `target_path`
3. 等 50ms 让对话框解析(与 H2 同一量级)
4. **还原原始文件名**
5. **读回证明还原成功** —— `SetValue` 返回 Ok 不算数,必须读回值完全相等
6. 两次机会;仍失败则 `error!` 明确报出当前脏值

新增 `restore_filename_verified()` 同时供 H2 复用,并因此顺带关闭了
「H2 假成功」这一已知限制(见 `extension-changelog.md`)。

**刻意不做的事**:还原失败时**不**累加 `unsupported_dialog_count`。
对话框是可达的、导航也做了,这是我们自己的收尾失败,不是「对话框类型不受支持」,
去动那个计数器会给用户弹出一条描述错误事情的提示。

## BUG-3 确认保存时报「路径不存在」,但目录确实存在 —— ✅ 随 BUG-2 关闭

**严重度:中**(是 BUG-2 的下游表现,不是独立问题)

### 现象(截图)

文件名框内容被改成 `线上培训\第4次线上培训纪要_2026-10-08` 后点「保存」,Windows 弹出:

```
线上培训\第4次线上培训纪要_2026-10-08
路径不存在。
请检查路径是否正确，然后重试。
```

### 成因

对话框当前目录已经是 `E:\办公文件\02 1号位\线上培训\第4次线上培训_2026-10-08`(地址栏正确),
但文件名框里带着 `线上培训\` 前缀。Windows 把 `线上培训\第4次线上培训纪要_2026-10-08`
当作**相对路径**去解析,自然找不到。

⇒ **修好 BUG-2,BUG-3 自动消失。** 2026-10-08 确认成立:BUG-3 没有独立成因,
它完全由 BUG-2 产生,因此本次未对 BUG-3 做任何独立改动。

## 三者的关系(2026-10-08 更正后)

```
        monitor 检测到前台是对话框(~300ms 之前)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   用户期间切到别的应用      用户一直留在对话框
        │                       │
        ▼                       ▼
  【BUG-1】SendInput 打到   对话框刚打开、WinUI 标记未就位
  别的进程并回车发送                │
        │                           ▼
        │                  is_winui3_wrapped = false
        │                           │
        │                           ▼
        │                  H1 / H2 整条链被跳过
        │                           │
        │                           ▼
        │                  【BUG-2】F3 把完整路径写进
  危害:向任意应用发消息     文件名框且从不还原 ← 真正的根因
                                    │
                                    ▼
                            【BUG-3】文件名框带路径前缀
                                        │
                                        ▼
                                   「路径不存在」报错
```

**BUG-1 与 BUG-2 不共享同一个前置条件。** 原文称二者共享「注入动作跨越焦点变化窗口
却没有在当下确认前台」,这对 BUG-1 成立,对 BUG-2 **不成立**:BUG-2 发生在用户全程
留在对话框、注入正常送达的情况下。BUG-2 的触发条件是**对话框尚未完全成型**,
而不是焦点变化。

## 修复方向 —— 全部已实施(v0.5.8)

原文列的三条方向,实际执行结果:

| # | 方向 | 状态 | 说明 |
|---|---|---|---|
| 1 | 发送前瞬时校验 | ✅ 已于 v0.5.7 实施 | 三道闸门(`IsWindow` + `is_file_dialog` + monitor 发布值),与 BUG-2 无关 |
| 2 | **H2 自验证:读回必须完全等于原始文件名** | ✅ 已实施 | `restore_filename_verified()`;同时供 F3 复用 |
| 3 | 对话框抖动处理 | ⏸ 未实施 | 见下 |

**方向 2 的实施范围比原文更大**:原文档以为问题出在 H2,因此只打算修 H2。
取证发现写脏字段的是 F3,而 F3 当时连还原都没有。因此修复覆盖了
**F3(新增还原+读回)与 H2(补上读回)** 两条路径,`inject_via_uia` 中所有会写
文件名框的分支现在都留下「要么干净,要么大声报错」的保证。

**方向 3 未做,理由**:`UIA error 0x80004005` 全历史出现 47 次,但同期 H1 成功 86 次。
它与写入成功率没有可观察的对应关系,贸然按它放弃写入,风险大于收益。
**未覆盖:抖动是否影响导航本身 —— 需要在真实弹窗中观察才能回答。**
