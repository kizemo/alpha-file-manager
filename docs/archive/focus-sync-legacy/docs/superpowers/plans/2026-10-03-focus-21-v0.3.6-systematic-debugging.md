## 0. TL;DR(60 秒)

5+ 轮 focus 修复全部失败,因为我们一直在修 **focus-sync 自己**(Sidecar Rust 逻辑、Extension UX 文案),**完全没修真正的根因**。本次 Phase 1-4 调查发现**两个独立的根因层**:

| Layer | 根因 | 严重度 | 谁负责 |
|---|---|---|---|
| **L1** | **Sigma FM sandbox reqwest 无 `.no_proxy()`** → 走系统 HTTPS_PROXY=63716(cc-haha)→ 502 | 🔴 HIGH | Sigma FM 上游 bug(不是 focus-sync) |
| **L2** | **focus-sync v0.3.x 强制写 WinUI filename 字段**(focus-20 恢复的逻辑)→ 用户拒收"filename 被修改" | 🔴 HIGH | focus-sync 架构缺陷 |
| L3 | 502 + filename 写入并存→ 用户既看不到 PUSH 成功(502),也阻止不了污染 | (combined effect) | — |

**v0.3.6 必修**:
1. **回归 focus-19 行为**:WinUI dialog → 不写 filename,只返回 `Unsupported`(focus-19 原本就是这样)
2. **文档化**:用户在 Edge 启用 legacy file picker flag 才能 100% work
3. **同时** Sigma FM sandbox 缺 `.no_proxy()` 是上游 bug,**不是 focus-sync 能修的**,但 focus-sync 应当告知用户

### 1.4 关键代码路径检查(无 502 来源!)


**Sigma FM Tauri 端和 focus-sync sidecar 端都没有任何 502 生成路径。** 502 必然来自第三方。

### 1.5 Sigma FM sandbox 关键代码路径

`sigma-file-manager/src-tauri/src/extensions/extension_http.rs`:

```rust
reqwest::Client::builder()
    .connect_timeout(Duration::from_secs(15))
    .redirect(reqwest::redirect::Policy::limited(5))
    .user_agent(HTTP_USER_AGENT)
    .build()
```

❌ **没有 `.no_proxy()` 调用**。

`reqwest 0.13.5`(Sigma FM Cargo.lock 中的版本)**默认遵守 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量,但不遵守 `NO_PROXY`**(除非显式 `.no_proxy()`)。

### 1.6 综合证据 → L1 根因成立

1. 用户截图扩展器 PUSH 收到 502
3. sidecar 端实际工作(curl 直接调返回 200)
4. Sigma FM sandbox 用 reqwest 无 `.no_proxy()`
5. 系统 `HTTPS_PROXY=127.0.0.1:63716`(cc-haha)
6. cc-haha 接受 TCP 连接但不响应 HTTP
7. reqwest 把请求路由到 cc-haha → cc-haha 处理失败 → reqwest 返回 502(具体行为需进一步验证)

### 1.7 综合证据 → L2 根因成立

1. v0.3.5(以及 v0.3.3/4)的 `uia_inject.rs::inject_via_uia` WinUI fallback 分支(L478-484):
   ```rust
   if let Some(ref edit) = best_edit {
       edit.GetCurrentPatternAs::<IUIAutomationValuePattern>(...)
           .SetValue(&BSTR::from(target_path))?;   // ← 写入 filename
   }
   ```
2. **N1 修复反而强化了这个写入**(同时加 commit)
3. 用户反馈"filename 仍被修改"= 写入行为存在 ✓

## 4. Phase 4.5 架构质疑(触发!5+ 轮无效)

### 4.1 真正的根因(系统层)

**5+ 轮 focus 修复无效的真正原因是 focus-sync 在错误的层修问题**:

| 我们修的 | 错的层 | 实际根因 |
|---|---|---|
| focus-17/20 改 focus-sync `uia_inject.rs` SetValue 行为 | 用户拒收"filename 写" | **架构假设错**(PathWrap 不适合 WinUI 3) |
| focus-18 加 Auto-Confirm toolbar | 不能解决 WinUI 不响应 Invoke | **同架构错** |
| focus-19 v0.3.2 删除 filename 写(返回 Unsupported) | 用户说"啥也没干" | **用户拒绝 partial fix,要么全 work 要么别动** |
| focus-21 v0.3.4/5 加 toolbar 按钮、grace period | 仍写 filename | **用户继续抱怨** |
| focus-21 v0.3.6 N1 加 WinUI Invoke | 仍写 filename | **用户继续抱怨** |

**用户明确传达(横跨 6 轮):"不要写我的 filename"。**

### 4.2 架构层方案对比

| 方案 | WinUI 行为 | Chromium 41477 | Edge legacy IFileDialog | 用户满意度 |
|---|---|---|---|---|
| **A: focus-19 行为(推荐)** | Unsupported(不写) | SetValue + (commit) | SetFolder COM | **🟢 高**(用户要的就是这个) |
| B: focus-20/21 当前行为 | SetValue + (commit) | SetValue + (commit) | SetFolder COM | 🔴 低(用户拒收) |
| C: 完全禁用 WinUI 路径同步 | 不注册 dialog | (不变) | SetFolder COM | 🟡 中(更保守) |
| D: 暂停 focus-sync for WinUI | (不变) | (不变) | (不变) | (no fix) |

**方案 A 是用户要的行为**。focus-19 v0.3.2 就是这个行为,只是当时没有 Edge legacy flag 通知,UX 差。**v0.3.6 应该回归 A + 加 Edge legacy flag 通知**。

### 4.3 用户的两难(也是 5 轮修改无效的核心)

```
用户想要的:
  - Edge WinUI Save As:focus-sync 自动同步路径(dialog 自动导航)OR 不动 dialog
  - 不允许的:filename 字段被悄悄写满路径文字
```

但 focus-sync 技术上无法 100% 让 WinUI 自动导航(PathWrap 架构限制),所以用户实际能选的只有:
1. focus-sync 不动 WinUI(返回 Unsupported)→ **focus-19 行为**
2. focus-sync 写 filename 让用户手动点 Save→ **focus-20 行为(用户拒收)**

**用户明确选 1**(基于 6 轮反馈推断)。

```rust
        .SetValue(&BSTR::from(target_path))?;   // ← 删除这行
```

```rust
        if let Err(e) = commit_via_uia(...) {
            warn!("...");
        }
    }
    // ...
```

→ commit_via_uia 调用保留(对 Chromium 41477 行为),但仅在 user-verify 确认 WinUI Invoke 行为后启用。**v0.3.6 暂时保持现状(41477 commit,WinUI 不写)**。
