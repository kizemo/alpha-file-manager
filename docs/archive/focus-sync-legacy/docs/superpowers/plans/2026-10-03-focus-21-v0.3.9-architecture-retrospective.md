## 1. 为什么基于成熟项目(PathWrap)还这么难 — 架构真相

### 1.1 PathWrap 设计时的 Windows 假设(全部已失效)

| PathWrap 假设(2020 时代) | 当前 Windows 11 22H2+ 现实 |
|---|---|
| Save As dialog = `#32770` class + 1001/1148 Edit + Invoke Save | `#32770` class 仍存在,但**内部被 WinUI 3 wrapper 包裹** |
| UIA SetValue 写入 filename = 真正写入 | SetValue 写入可能被 WinUI wrapper 拦截、延迟、或显示中间态后回滚 |
| Invoke Save = 真正提交 | 部分 WinUI dialog 屏蔽外部 Invoke,需要 Enter 键事件 |
| dialog 创建时 IFileDialog 接口可被发现 | WinUI 3 wrapper 在外层,内层 IFileDialog 通过 `AccessibleObjectFromWindow(OBJID_NATIVEOM)` 不再稳定可访问 |
| UIA 一次性 inventory + 决策 | WinUI 3 dialog 在创建后 100-500ms 内 UIA 树结构还在变化,SetValue 时机难把握 |

**PathWrap 是为"老 Windows"写的** — 它在 Windows 10 LTSC 2019 / Server 2019 上**可能**完美工作。但 Win11 22H2+ 改变了底层规则。

### 1.2 WinUI 3 Wrapped Dialog 的本质问题

**WinUI 3 wrapped dialog 长这样**(从 UIA 视角):
```
WinUI 3 wrapper (Pane 50003, automation_id="FileNameControlHost")
  └─ 内部 IFileDialog (#32770)
      ├─ 1001 Edit (真正的 filename Edit, SetValue 可写但不生效)
      ├─ 1148 ComboBox
      └─ Save button
```

**关键事实**:
1. **外层 class 是 `#32770`** — 所以 `app:#32770` 误判为 legacy IFileDialog
2. **UIA tree 里 1001/1148 Edit 都存在** — 所以 `find_ifiledialog_edit` 匹配成功
3. **SetValue 在 UIA 层面成功** — read back 也对得上 → `path_matches` 验证通过
4. **但 WinUI 3 wrapper 在中间层做了 routing**:
   - 写入可能延迟到下个渲染周期才显示
   - 显示 2-6 秒后被 WinUI 自己覆盖回原值
   - Invoke Save 可能真正 work(dialog 关闭)但用户在 2-6 秒窗口看到"filename 被改"

**这不是 bug,是 Microsoft 的 design**:WinUI 3 dialog 是有状态机管理的,UIA SetValue 是异步事件。

### 1.3 Listary 为什么能做(我们为什么不能)

| Listary 的能力 | 我们做不到的原因 |
|---|---|
| **SetWindowLongPtr subclassing** 在 dialog 创建后立即 hook `WndProc`,拦截所有键盘/鼠标消息 | 反病毒软件会标记(subclassing 是经典 malware 模式);Windows Store 政策禁止;GitHub 公开仓库会被 AV 引擎扫描 |
| **未文档化 IFileDialog COM 方法**(`IFileDialog2::SetFolder2`, `IFileSaveDialog` interface) | 反编译需要 IDA Pro + 时间;Microsoft 法务风险 |
| **20+ 年 Windows internals 经验** | 团队规模差距 |
| **商业产品,有人工支持** | 用户自助 |
| **全球装机量驱动 bug 发现** | 我们只能在自己机器上测试 |

**Listary 不是"更聪明的 UIA"**,它走的是**完全不同**的技术路线 — 我们复制 UIA 部分,但那部分是 Listary 的**最后手段 fallback**。

## 3. 真正能解决路径同步的 5 条路线(诚实评估)

### 路线 A:接受现状(UIA-only,WinUI 3 不支持)

**做法**:
- v0.3.9 就是这个方向
- 把"WinUI 3 wrapped 不支持"做成**显式产品定位**
- 文档写清楚:Edge Modern / Photos / Paint / WinUI 3 apps 需要开启 legacy flag
- 提供一键脚本帮用户开 flag

**预期效果**:
- 对 Notepad/Photos(用 legacy dialog):✅ 完全工作
- 对 Edge Modern Save As:❌ 不工作,提示开 flag
- 对 Chromium 41477:✅ 完全工作
- 对 Win11 22H2+ Edge/Photos/Paint:❌ 不工作

**诚实评分**:3/10(解决 30-50% 场景,核心 Edge 用例失败)

**风险**:用户持续 reject("还是不能同步")。**这不是工程问题,是产品定位问题**。

---

### 路线 B:浏览器扩展方案(JS File System Access API)

**做法**:
- 不动 sidecar 架构
- 给 Edge / Chrome 写一个**真正的浏览器扩展**(用 Chrome Web Store / Edge Add-ons 渠道)
- 扩展监听 Sigma FM 的 HTTP 推送(改为 WebSocket 或 polling)
- 扩展调用 **`window.showSaveFilePicker()`** — 这是 Chrome/Edge 95+ 原生 API
- 这个 API 直接打开 native file picker,**UIA 不需要工作**

**预期效果**:
- 对 Edge / Chrome 的"另存为":✅ 完全工作(浏览器 API 路线)
- 对 Edge 的"下载":✅ 工作
- 对 Firefox / Safari:仍 UIA 路线(部分工作)
- 对 native app(Notepad/Photos):仍 UIA 路线(部分工作)

**诚实评分**:7/10(解决 60-70% 现代场景,但**不是 OS-level helper**,而是浏览器工具)

**风险**:
- 需要 Edge Add-ons 开发者账号($0)
- 浏览器扩展 sandbox 限制可能阻碍 IPC
- **架构转变** — 不再是"OS 路径同步工具",而是"浏览器扩展"

---

### 路线 C:Explorer 接管方案(drag-and-drop 范式)

**做法**:
- 不驱动 dialog,直接关闭它(或后台运行)
- 在 Explorer 中打开目标文件夹(`explorer.exe /e,"C:\evid"`)
- 用户从 Explorer 拖文件到 Save As dialog

**预期效果**:
- 对所有 dialog:✅ 可用(Explorer 始终能开)
- 用户体验:从"自动"变成"半自动",需要拖一次

**诚实评分**:5/10(技术可靠,但 UX 倒退 — 失去"自动导航"卖点)

**风险**:Sigma FM 的核心卖点是"无缝跟随",这路线等于承认做不到

---

### 路线 D:Windows Subclassing(高风险高回报)

**做法**:
- sidecar 启动一个 hook DLL,注入到每个新建的 dialog 进程
- 用 `SetWindowsHookEx(WH_CALLWNDPROC)` 拦截 `WM_INITDIALOG` / `WM_NCCREATE`
- 在 dialog 完成初始化**之前**注入目标路径

**预期效果**:
- 对所有 dialog:✅ 完美工作(类似 Listary)
- 用户体验:1-2ms 延迟,无感知

**诚实评分**:9/10(理论上最佳方案)

**风险**:
- ⚠️ **反病毒软件会标记** — DLL injection 是经典 malware pattern
- ⚠️ **Windows Defender SmartScreen** 可能阻止启动
- ⚠️ **企业 EDR 产品**(Defender for Endpoint、CrowdStrike)会告警
- ⚠️ **Windows Store 政策禁止** — 这个产品不能上架 Store
- ⚠️ **GitHub 公开仓库** — AV 扫描可能把整个仓库标记
- ⚠️ **可能违反 Windows TOS**(ToS §3.2 "you may not ... interfere with the operation of any software")

**结论**:技术可行,**法律/政策/安全风险不可接受**。Listary 是商业闭源软件,我们是开源。

---

### 路线 E:范式转换 — 不再"驱动 dialog",改为"提供目标文件夹快捷方式"

**做法**:
- sidecar 检测 dialog 后,**关闭它**
- 弹出 toast:"Sigma FM 路径 C:\evid 已打开,请重新触发 Save As"
- 临时 hook 键盘,等 Ctrl+S 时**预先设置剪贴板路径**,这样粘贴的就是目标文件夹

**预期效果**:
- 对所有 dialog:✅ 可靠
- 用户体验:多 1-2 步,但 100% 可靠

**诚实评分**:6/10

**风险**:剪贴板操作可能触发 AV 警告

## 4. 我对最佳路线的建议

### 短期(本周)— 不再迭代 UIA

1. **冻结 v0.3.9** 作为 baseline(它不污染 filename)
2. **明确产品定位**:focus-sync = "Chromium Save As + Legacy IFileDialog path sync" + "WinUI 3 wrapped → unsupported"
3. **更新扩展文档**:每个用户看到"Sidecar not reachable"通知时,告诉他开 `edge://flags/#edge-legacy-file-picker`
4. **加 metric 计数**:每天 unsupported_dialog_count 写到日志,统计用户实际被影响的场景比例

### 中期(下个月)— 路线 B(浏览器扩展)

如果你能接受"从 OS helper 变成浏览器扩展",这是**目前技术上最可行的、能解决 60-70% 现代场景的方案**。

需要的改动:
- 新建 `release/edge-extension/` 目录
- 注册 Edge Add-ons 开发者账号
- 用 `manifest.json v3` + service worker
- 改 sidecar → 加 WebSocket endpoint(`/subscribe`)
- 浏览器扩展订阅 WebSocket,收到路径后调用 `window.showSaveFilePicker({ suggestedName })`

### 长期(未来)— 路线 D 风险评估

如果用户接受反病毒警告 + Windows Store 下架 + ToS 风险,路线 D 才是真"100% 解决方案"。但**这意味着产品形态从"公开开源软件"变成"半商业工具"**。

## 5. 我承诺不做的(避免再来一轮)

基于 systematic-debugging Phase 4.5(3+ fixes 失败 → 质疑架构,不要继续 fix):

1. ❌ **不再加更多 UIA helper**(is_winui3_v2, is_winui3_v3, etc.) — 已证明 UIA 路线走不通
2. ❌ **不再"基于 PathWrap 魔改"** — PathWrap 的基础假设已失效
3. ❌ **不再承诺"v0.3.x 能 sync Edge WinUI 3"** — 这个目标架构上不可达
4. ❌ **不再用 PUSH=200 当成功信号** — PUSH=200 只代表 HTTP 通,不代表 dialog 跳了。诚实指标是 dialog_closed 之后用户无需手动操作
5. ❌ **不再做"小修小补"** — 任何 fix 必须基于"完整 root cause 证据链",否则就是 symptom-fixing
