## 0. TL;DR(60 秒)

**v0.5.1 SendInput 在 sidecar 单独进程内有结构性限制**(Mavis 第 13 轮 D3 [HIGH]):

| 因素 | 影响 |
|---|---|
| spike.exe 启动方式 | 用户态 Scheduled Task (`KizemoFocusSync` / AtLogOn) |
| 启动后是否收到 foreground | **从未**(只跑 HTTP server + UIA poll) |
| `SetForegroundWindow(dialog)` 在 Vista+ | **大概率失败**(foreground 锁定规则) |
| `AllowSetForegroundWindow` 调用方 | **需要接收方调用**,spike 自调无效 |
| `SendInput` 目标 | foreground 线程的 input queue(不是 spike 自己) |
| **实际效果** | **SendInput 路径在 sidecar 内大概率失败** |

**v0.5.1 实施选择**:**方案 C**(尽力 + 多层 fallback,不假设 SendInput 一定 work)。

**长期架构选择(留给后续会话 / 架构师)**:
- **方案 A**:Sigma FM extension 直接 SendInput(extension 有 foreground 权限)
- **方案 B**:Sigma FM extension 转发 SendInput 命令到 sidecar
- 详细对比见 §3

## 1. 核心问题:为何 sidecar 不能 SendInput

### 1.1 Windows Vista+ 的 foreground 锁定规则

Windows Vista 引入的 `SetForegroundWindow` 限制(MSDN `SetForegroundWindow` Remarks):

> "The system restricts which processes can set the foreground window. A process can set the foreground window only if **the foreground process has not locked the foreground** within the last 200ms, OR **another process has called `AllowSetForegroundWindow`** to grant permission."

具体规则:
1. 只有「**曾收到 foreground 的进程**」或「**被 `AllowSetForegroundWindow` 显式允许**的进程」才能 `SetForegroundWindow`
2. `AllowSetForegroundWindow(dwProcessId)` 是**接收方进程**调用的 API(让目标进程可以设 foreground)
4. 反向调用(spike 自己调 `AllowSetForegroundWindow`)无效

### 1.2 spike.exe 的启动模型

`KizemoFocusSync` Scheduled Task 的设计:
- **触发**: AtLogOn(用户登录时)
- **执行**: 已使用 `Users` 权限运行(spike.exe 不需要 admin)
- **运行模型**: 持续监听 `127.0.0.1:37421`,等待 SIGMAFM extension 的 HTTP POST
- **UIA 工作**: 后台 poll 已注册 dialog 窗口(不弹窗、不抢 foreground)
- **foreground 历史**: **从未**(spike.exe 从启动到死亡都没收到过 foreground)

### 1.3 真实运行场景

用户在 Edge Modern Save As:
```
用户操作流程:
  1. 用户在 Edge 浏览器中按 Ctrl+S
  2. Edge 弹出 Save As dialog(foreground = Edge / WinUI 3 wrapper)
  3. 用户在 Sigma FM 中点击 folder
  4. Sigma FM extension 通过 HTTP POST /set_path 通知 spike
  5. spike 调用 SetForegroundWindow(dialog) → 失败(没 foreground 历史)
  6. spike 调用 SendInput Ctrl+L → 失败(焦点不在 dialog)
  7. **用户视觉上 dialog 没动,breadcrumb 没更新**
```

**SendInput 路径在 sidecar 实际不可行**(高).

## 2. v0.5.1 实施选择 — 方案 C

### 2.1 已实施的策略

```rust
// uia_inject.rs::try_send_path_via_sendinput
fn try_send_path_via_sendinput(dialog_hwnd: u32, target_path: &str) -> bool {
    let hwnd = HWND(dialog_hwnd as *mut core::ffi::c_void);
    unsafe {
        // D1 [HIGH]: ASFW_ANY = 0xFFFFFFFF (正确常量)
        let _ = AllowSetForegroundWindow(ASFW_ANY); // 无效但保持完整性
        // SetForegroundWindow 在 foreground 锁定规则下大概率失败
        let _ = SetForegroundWindow(hwnd);
        // SendInput Ctrl+L + path + Enter(尽力)
        let n = SendInputFn(&inputs, ...);
        if n != inputs.len() as u32 {
            // 部分事件被系统拒绝 → 走 H2 fallback
            return false;
        }
        true
    }
}
```

**关键**:SendInput 失败不视作 bug,fallback 到 H2 / v0.5.0 / Unsupported。

### 2.2 多层 fallback chain(已实施)

```
Layer 1: COM IFileDialog::SetFolder (Vista+ IFileDialog 原生)
  ├─ success → DialogOutcome::ComSetFolder (Edge Legacy / Photos / Notepad)
  └─ fail → Layer 2

Layer 2: WinUI 3 wrapped 检测
  ├─ 检测到(has_filename_host ∧ has_1001)→ 4 层 fallback:
  │   ├─ H1: SendInput Ctrl+L + path + Enter (尽力)
  │   │   ├─ success → DialogOutcome::AddressBarWritten (clean filename)
  │   │   └─ fail → H2
  │   ├─ H2: SetValue target_path → SetValue original filename (50ms 闪烁)
  │   │   ├─ success → DialogOutcome::AddressBarWritten (breadcrumb 更新)
  │   │   └─ fail → F3
  │   ├─ F3: v0.5.0 SetValue 1001 + Invoke Save (filename 污染已知)
  │   │   └─ success → DialogOutcome::AddressBarWritten (best-effort)
  │   └─ 全失败 → F4
  └─ 不检测到 → Layer 3

Layer 3: 普通 UIA fallback (Chromium 41477 / 普通 1001)
  └─ best_edit SetValue + best_button Invoke → DialogOutcome::AddressBarWritten

Layer 4: Unsupported → state.inc_unsupported_dialog_count (extension 通知)
```

**保证**:v0.5.1 永远不会比 v0.5.0 更差。SendInput 失败只是 H2 fallback,最终还是回到 v0.5.0 行为。

### 2.3 PUSH dedup (D6)

`http_server.rs::handle_set_path` 加入 path 不变检测:
```rust
if state.get_current_path() == path {
    log_event("set_path_dedup");
    return respond_json(200, ok); // 不调用 write_path,避免 SendInput 干扰用户
}
```

**作用**:用户反复点同一路径时,不会触发多次 SendInput(Ctrl+L 会清空用户输入的 filename)。

## 3. 长期架构方案(后续决策)

#### 方案 A:Sigma FM extension 直接 SendInput

**架构**:
- Sigma FM extension(JS)在 Sigma FM 进程内运行
- Sigma FM 进程在 foreground 时可以 `SetForegroundWindow` 任意窗口
- extension 直接调用 Win32 API (`chrome.devtools` 或 Web API 没有 SendInput,需要 manifest permission + extension JS sendInput 库)
- sidecar 只负责:Win32 IFileDialog、Chromium 41477、其他无 foreground 限制路径

**优点**:
- ✅ extension 在 foreground 进程,**有 foreground 权限**
- ✅ extension 已经知道 dialog (UIA 找到 + Sigma FM UI 选中)
- ✅ 用户已经在 Sigma FM 中操作,不需要跨进程

**缺点**:
- ❌ JS SendInput 库需要 native messaging 或 chrome.windows API
- ❌ manifest 需要 `"nativeMessaging"` 或 `"debugger"` permission
- ❌ 复杂架构改动(超出 v0.5.1 范围)

**实施工作量**:**2-3 周**(含 manifest + native messaging helper + 测试)

#### 方案 B:Sigma FM extension 转发 SendInput 命令到 sidecar

**架构**:
- extension 收到 Sigma FM 路径变化 → HTTP POST /send_path sidecar
- sidecar 收到后,先通过 IPC 让 extension 执行 `SetForegroundWindow + SendInput`
- extension 在 Sigma FM 进程内执行(foreground 上下文)

**优点**:
- ✅ sidecar 仍负责所有 Win32 工作
- ✅ SendInput 部分由 extension 执行(foreground 端)

**缺点**:
- ❌ 双向 IPC 复杂(extension → sidecar + sidecar → extension)
- ❌ 路径不一致 race window

**实施工作量**:**1-2 周**

#### 方案 C(已实施):sidecar 尽力 + 多层 fallback

**架构**:sidecar 直接 SendInput,接受大概率失败,fallback 到 v0.5.0 SetValue。

**优点**:
- ✅ 0 架构改动
- ✅ v0.5.1 已实施 + 已通过 compile + test

**缺点**:
- ❌ SendInput 大概率失败(用户视觉上 dialog 不动)
- ❌ 实际效果 = v0.5.0(breadcrumb work 但 filename 污染)
- ❌ **没满足用户核心诉求**(完全不动 filename)

**实施工作量**:**已完成**(本 handoff)

## 5. 硬规则新增(规则 47-48)

**规则 47**(本次实施沉淀):**SendInput helper 必须完整实现**(`make_key` / `make_unicode` 函数体,不能用 `/* ... */` 占位符)— 否则编译通过后无法 test。

**规则 48**(本次实施沉淀):**任何 "X 进程做 Y 操作" 方案,先 verify X 是否有 Y 权限** — spike.exe 是 Scheduled Task 启动的后台进程,没有 foreground 历史,SendInput 在 sidecar 内不可行。

## 6. 不要做(避免再次误判)

- ❌ 假设 sidecar 可以 `SetForegroundWindow` 任意窗口(Vista+ 限制)
- ❌ 假设 `AllowSetForegroundWindow` spike 自调有效(需要接收方调)
- ❌ 假设 SendInput 在 sidecar 一定 work(基于 session 0 + foreground 历史)
- ❌ 假设 Foreground 进程可以跨进程 SPI/async SendInput(spike 不是 foreground)
- ❌ 假设 WinUI 3 wrapped 检测一定会识别(可能因 WinUI 版本变化而失效)
