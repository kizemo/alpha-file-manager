## 2. v0.5.1 plan 9 处需要调整

### 2.1 🔴 D1 [HIGH] — `AllowSetForegroundWindow` 第一个参数错

**v0.5.1 §4.1 代码**:
```rust
let _ = windows::Win32::UI::WindowsAndMessaging::AllowSetForegroundWindow(0x00000001); // ASFW_ANY
```

**问题**:
- 注释说 `0x00000001` 是 ASFW_ANY
- 实际 ASFW_ANY = `0xFFFFFFFF`(DWORD)(-1)
- `0x00000001` 是不正确的常量(可能是 ASFW_PROCESS_ID 但也不对)

**正确用法**:
```rust
// D1 [HIGH]: AllowSetForegroundWindow(ASFW_ANY) 允许任何进程 set foreground
let _ = AllowSetForegroundWindow(ASFW_ANY);
// 或直接用常量
const ASFW_ANY: u32 = 0xFFFFFFFF;
```

**额外问题**:Vista+ 的 foreground 锁定规则 — **spike.exe 在 Scheduled Task 启动,从未收到过 foreground,`AllowSetForegroundWindow` 可能无效**。
- **解决**:`AllowSetForegroundWindow` 通常是接收方调用(谁需要让 spike 设 foreground)— spike 调用本身无效
- 实际:foreground 锁定规则是 `AllowSetForegroundWindow`(接收方允许 spike)+ `SetForegroundWindow`(spike 申请)
- **spike 必须先收到 foreground 或被允许**(否则 SetForegroundWindow 失败)

### 2.2 🔴 D2 [HIGH] — SendInput 实现细节缺失

**v0.5.1 §4.1 代码**:
```rust
fn make_key(vk: u16, flags: u32) -> INPUT { /* ... */ }
fn make_unicode(ch: u16) -> INPUT { /* KEYBD_EVENTF_UNICODE */ }
```

**问题**:
- 两个 helper 函数没实现
- KEYBD_EVENTF_UNICODE 应该是 `KEYBD_EVENTF(0x0004)` 或 `KEYEVENTF_UNICODE`(windows crate API)
- SendInput 输入 INPUT 数组,每个 INPUT 含 type + u.mi 或 u.ki

**完整实现**(D2):
```rust
fn make_key(vk: u16, flags: u32) -> INPUT {
    let mut input = INPUT::default();
    input.r#type = INPUT_KEYBOARD;
    unsafe {
        let ki = windows::Win32::UI::Input::KeyboardAndMouse::KEYBDINPUT {
            wVk: VIRTUAL_KEY(vk),
            wScan: 0,
            dwFlags: KEYBD_EVENTF(flags),
            time: 0,
            dwExtraInfo: 0,
        };
        input.Anonymous = std::mem::zeroed();
        // 这里需要 unsafe set Anonymous.ki = ki
        // 实际 windows 0.62 API:
        *input.Anonymous.ki_mut() = ki;
    }
    input
}

fn make_unicode(ch: u16) -> INPUT {
    let mut input = INPUT::default();
    input.r#type = INPUT_KEYBOARD;
    let ki = KEYBDINPUT {
        wVk: VIRTUAL_KEY(0),
        wScan: ch,
        dwFlags: KEYBD_EVENTF_UNICODE,
        time: 0,
        dwExtraInfo: 0,
    };
    unsafe { *input.Anonymous.ki_mut() = ki; }
    input
}
```

**作用**:提供完整 helper 实现,避免 Claude 必须重新实现。

**工作量**:10 min(测试 + 调试 SendInput 是否真到达 dialog)

### 2.3 🔴 D3 [HIGH] — 架构反思:sidecar 单独进程 SendInput 难成功

**核心问题**:
- sidecar 是 **Scheduled Task 启动的独立进程**
- Vista+ 的 foreground 锁定规则:**只有"曾收到 foreground 的进程"或"被 AllowSetForegroundWindow 显式允许"的进程**才能 SetForegroundWindow
- spike.exe 启动后**从未收到 foreground** → SetForegroundWindow 会失败
- 即使 AllowSetForegroundWindow(ASFW_ANY) 也需要**接收方调用**(不是 spike 自己)
- 实际架构:Sigma FM 在前台,Sigma FM extension 是 foreground 进程,但 spike.exe 不是

**真实场景**:
- 用户在 Edge Save As dialog(foreground)
- Sigma FM 在后台
- sidecar(spike.exe)收到 HTTP PUSH → 想 SetForegroundWindow(dialog) → **失败**(没 foreground 权限)
- SendInput Ctrl+L → **失败**(焦点不在 dialog)
- 实际效果:**SendInput 路径在 sidecar 单独进程中根本无法工作**

#### 修复方案 — 2 个选项

**方案 A**:**Sigma FM extension 直接 SendInput**
- Sigma FM extension 是 Sigma FM 进程内的 JS,**有 foreground 权限**
- extension 已经知道 dialog (UIA 找到 + Sigma FM UI 选中)
- extension 直接调用 chrome.devtools API 或新 JS SendInput API(可能需要新 manifest permission)
- sidecar 只负责 Win32 IFileDialog / 41477 / 其他无 foreground 限制路径
- **架构调整** — 不是修 bug,是**重新分配责任**

**方案 B**:**Sigma FM extension 转发 SendInput**
- sidecar 通过 HTTP 告诉 extension:"请执行 SendInput"
- extension 收到命令后,在 Sigma FM 进程内执行 SendInput
- 仍需要 Sigma FM extension 有 foreground 权限(方案 A 同)

**方案 C**:**接受 SendInput 在 sidecar 不工作**
- sidecar 通过 SetForegroundWindow + AllowSetForegroundWindow(尽力)
- 失败时 fallback 到 H2(恢复 filename)
- H2 失败时 fallback 到 v0.5.0(已知部分 work 但 filename 污染)
- **v0.5.1 实施时,不假设 SendInput 一定 work**

#### 推荐

**方案 A 最优**(架构调整):
- Sigma FM extension 是唯一有 foreground 权限的进程
- SendInput 必须在 Sigma FM 进程内执行
- 这意味着 v0.5.1 的 `send_path_via_sendinput` 函数**不应该在 sidecar 内**,应该在 Sigma FM extension JS 内
- sidecar 通过 HTTP 响应告知 extension "请 SendInput",或 Sigma FM extension 自己做 UIA 检测

**但**:**方案 A 需要架构改动**,可能不在 v0.5.1 范围。

**方案 C 是 v0.5.1 范围**(实施但不假设 SendInput work):
- sidecar 实施 SendInput(尽力)
- fallback chain:SendInput → H2 → v0.5.0 → Unsupported
- 如果 SendInput + H2 都 fail,fallback 到 v0.5.0(已知部分 work)

### 2.4 🟡 D4 [MEDIUM] — Hypothesis 2 (恢复 filename) Chromium 行为不确定性

**v0.5.1 §4.2 H2 风险**:
> Chromium 是否在 filename 回写时也回退 breadcrumb,需要实测验证。

**问题**:
- H2 假设:Chromium breadcrumb 在 filename 回写时保持
- 实际:**Chromium 可能每次 SetValue 都重新计算 breadcrumb**
- 如果 H2 实测失败,breadcrumb 会"reset"到原始值 → 副作用比 v0.5.0 更糟

**修复方案**:
```rust
// D4 [MEDIUM]: H2 必须先 verify Chromium 行为
// 实测方法: SetValue target_path → SetValue 原始 filename → 1 秒后检查 breadcrumb
// 如果 breadcrumb 已 reset 到原始 → H2 fail,fallback 到 v0.5.0

if has_filename_host && has_1001 {
    // 测试 H2 是否 work
    let edit = find_ifiledialog_edit(&elements).unwrap();
    let value_pattern = unsafe { edit.GetCurrentPatternAs(UIA_ValuePatternId)? };
    let original_filename = unsafe { value_pattern.CurrentValue() }?.to_string();
    
    // SetValue target_path
    unsafe { value_pattern.SetValue(&BSTR::from(target_path))? };
    std::thread::sleep(std::time::Duration::from_millis(50));
    
    // 立即恢复 original_filename
    unsafe { value_pattern.SetValue(&BSTR::from(original_filename.as_str()))? };
    std::thread::sleep(std::time::Duration::from_millis(50));
    
    // Read back breadcrumb(可能需要其他控件的 name 或 value)
    // 如果 breadcrumb 仍 target_path → H2 work
    // 如果 breadcrumb reset → H2 fail
}
```

**工作量**:D4 应作为 v0.5.1 实施的**前置 verification**,不是实施后再验证。

### 2.6 🟡 D6 [MEDIUM] — 多次 PUSH 触发多次 SendInput

**v0.5.1 §R76 风险**:
> 多次 PUSH 触发多次 SendInput(用户切路径)| 高 | 误操作

**问题**:
- 用户在 Sigma FM 中切路径 A → B → A → B
- 每次 PUSH 都触发 SendInput Ctrl+L + 输入路径
- 如果 dialog 还显示前次结果,**多次 SendInput 会破坏用户当前操作**
- 实际:用户在 dialog 中输入文件名,SendInput Ctrl+L 会清空输入框

**修复方案**:
- 加 PUSH dedup:`if path == last_pushed_path { skip SendInput }`
- 或在 PUSH 前 verify path 变化

**实施位置**:`http_server.rs::handle_set_path`
```rust
// D6 [MEDIUM]: PUSH dedup
let last_path = state.get_current_path();
if last_path == path {
    info!("PUSH: path unchanged, skipping");
    return respond_json(request, 200, &ok_response);
}
```

**作用**:避免重复 PUSH 触发多次 SendInput 干扰用户。

### 2.9 🟢 D9 [LOW] — Chromium 41477 vs WinUI 3 wrapped SendInput 差异

**问题**:
- Chromium 41477 Save As(无 WinUI 包裹)有独立的 address bar Edit
- WinUI 3 wrapped Edge Save As 没有独立 address bar(1001 双角色)
- SendInput Ctrl+L 在两种 dialog 上**可能行为不同**:
  - Chromium 41477: Ctrl+L 可能 focus search box 或无反应
  - WinUI 3 wrapped: Ctrl+L 应 focus 1001 Edit(双角色中的 address bar)

**修复方案**:
- v0.5.1 不假设 SendInput 在所有 dialog 都 work
- 加 dialog type detection:
  - WinUI 3 wrapped(`FileNameControlHost` 存在)→ SendInput Ctrl+L → path → Enter
  - Chromium 41477 → 已有 SetValue 路径(不 SendInput)
  - 其他 → fallback

**实际**:`inject_via_uia` 已经有 41477 分支(L439-453),WinUI 3 wrapped 检测应在其后。
