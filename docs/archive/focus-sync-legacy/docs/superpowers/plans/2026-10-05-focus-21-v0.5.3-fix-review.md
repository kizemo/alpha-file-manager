## 2. 🔴 A1 删 SetForegroundWindow 是严重回归

### 2.1 SendInput 投递路径

**关键事实**:SendInput **不是**直接发给特定 HWND,而是发到**调用线程的 input queue**,然后由 OS **dispatch 到当前 foreground 窗口的对应控件**。

```
sidecar thread → SendInput → 调用线程 input queue → OS dispatch → foreground 窗口
```

### 2.2 删除 SetForegroundWindow 后的事件路径

**Scenario A**:用户已点 dialog(dialog 是 foreground)
- SendInput Ctrl+L → dialog receives → Ctrl+L focus address bar ✓
- SendInput Home → cursor to start ✓
- SendInput Shift+End → select all ✓
- SendInput path → typing replaces ✓

**Scenario B**:用户在 Sigma FM 中导航(Sigma FM 是 foreground)
- SendInput Ctrl+L → **Sigma FM receives** → Sigma FM 内部 Ctrl+L handler(可能没绑定)
- SendInput Home → Sigma FM 搜索框 cursor 到行首 ❌
- SendInput Shift+End → Sigma FM 搜索框选中 ❌
- SendInput path → **Sigma FM 搜索框被填上路径** ❌
- dialog 完全没反应

### 2.3 用户实际场景大概率是 Scenario B

**复盘**:用户说 "切换到 Sigma FM 后,焦点会自动切换回下载弹窗"。

含义:用户**期望**留在 Sigma FM 工作,但 sidecar 把焦点拉回 dialog(违反用户期望)。

如果删 SetForegroundWindow:
- 焦点**不再被拉回** → 用户的"焦点盗窃"问题解决
- 但 SendInput 不再可靠到达 dialog → **新 bug:address bar 不更新**

**最坏情况**:用户切到 Sigma FM,等几秒,看不到 dialog 更新,以为没工作。手动点回 dialog,这次 PUSH 已经被错过,需重新触发。

### 2.4 修正建议(保留 SetForegroundWindow)

```rust
fn try_send_path_via_sendinput(dialog_hwnd: u32, target_path: &str) -> bool {
    let hwnd = HWND(dialog_hwnd as *mut core::ffi::c_void);
    unsafe {
        // 保留 SetForegroundWindow — 它通常是 no-op,但在某些情况能 work
        let _ = AllowSetForegroundWindow(ASFW_ANY);
        let _ = SetForegroundWindow(hwnd);
        
        // 检查是否真的拿到 foreground(GetForegroundWindow 比较)
        let current_fg = GetForegroundWindow();
        if current_fg != hwnd {
            warn!("v0.5.3 SendInput: dialog is not foreground (current_fg={current_fg:?}); events may not reach");
            // 不 abort — 仍尝试 SendInput,可能用户后续手动 focus
        }
        
        // ... rest of SendInput ...
    }
}
```

这样:
- SetForegroundWindow 尝试 + 失败 → 不发生焦点切换(no-op)
- SetForegroundWindow 成功 → **这是用户期望**("dialog 真正跳转"需要 dialog 在前台)
- **焦点盗窃只发生在 extension 调用 AllowSetForegroundWindow 时** — 那是 extension 的责任

### 2.5 真正修复"焦点盗窃"应在 extension 端

**位置**: `release/extension/dist/index.js` 的 `pushNow` 函数

**修复**:删 `allowSetForegroundWindow(sidecarPid)` 调用,或者改用 `AllowSetForegroundWindow(ASFW_ANY)` 减少权限传递。

**但 plan §6 禁止改 extension**("❌ 改 extension index.js 与 bug 无关")。这是误判 — extension 的 AllowSetForegroundWindow 是焦点盗窃的**真正原因**,不删它焦点盗窃会继续**。**

## 3. 🔴 A2 Ctrl+L 实际 focus 行为未知

### 3.1 关键问题

**plan 推断**:
> "**WinUI 3 wrapped dialog 拦截模式**... Ctrl+L 只 focus,不 select-all"

但 v0.5.2 的 user 实测:
> "SendInput 完全成功(events 全被接受),但拼接仍发生。说明: Ctrl+L focus 成功(到某处)"

**关键未回答问题**:
- Ctrl+L focus 的**哪里**?
  - Option X: focus 到 1001 Edit(filename box) → Home/Shift+End 操作 1001 → **filename 污染**
  - Option Y: focus 到 address bar(WinUI 3 hidden Edit) → Home/Shift+End 操作 address bar → 干净

### 3.2 验证方法

**实施前必做**(plan §9.2 缺):
- 实施 Home+Shift+End 后,**用 UIA read back** 当前 focused element
- 如果是 1001(Edit control with name "File name") → **污染风险,放弃**
- 如果是 address bar / BreadcrumbBar → 干净

**代码示例**:
```rust
// 在 try_send_path_via_sendinput 末尾加 read-back verify
let focused = unsafe { GetFocus() };  // focused HWND
let focused_elem = automation()?.ElementFromHandle(focused)?;
let focused_aid = current_automation_id(&focused_elem);
info!("v0.5.3 SendInput: focused element aid={focused_aid}, name={}", current_name(&focused_elem));
```

如果 aid == "1001" → emit warning, 不要继续。

### 3.3 为什么 plan 漏了 UIA read-back

**focus-19 + 后续 review 的教训**: **UIA read-back 可能不准**。WinUI 3 wrapped 的某些 element 名称是 hidden 或 virtualized,读 back 不可靠。

**但**:对 Ctrl+L focus 验证,这是必要的(否则可能污染 filename)。

**建议**:不依靠 UIA,改用 **`GetFocus()`** (Win32 API) + `GetClassNameW()` 看 focused 窗口类:
```rust
unsafe {
    let focused = GetFocus();
    let mut class_name = [0u16; 256];
    let len = GetClassNameW(focused, &mut class_name);
    let class = String::from_utf16_lossy(&class_name[..len as usize]);
    info!("v0.5.3: focused class = {}", class);
}
```

如果 class 是 "Edit" → focused 是 Edit 控件。
如果 class 是 "ComboBox" → filename combo box。
如果 class 是其他 → 可能 address bar 或自定义。

## 4. 🟡 A3 Shift+End 时序错了

### 4.1 plan 当前代码

```rust
// v0.5.3
inputs.push(make_key(VK_HOME.0, 0));
inputs.push(make_key(VK_HOME.0, KEYEVENTF_KEYUP.0));
inputs.push(make_key(VK_SHIFT.0, 0));
inputs.push(make_key(VK_END.0, 0));
inputs.push(make_key(VK_END.0, KEYEVENTF_KEYUP.0));
inputs.push(make_key(VK_SHIFT.0, KEYEVENTF_KEYUP.0));
```

### 4.2 问题

这是 **Home(无 modifier) + Shift+End(modifier)**。**没问题**。

但是考虑 Windows 处理修饰键的细节:
- 修饰键(Shift)按下时,如果目标应用检测 Shift 状态,**可能要求 Shift down 在 End 之前 N ms**

plan 是 Shift↓ → End↓ → End↑ → Shift↑。时间间隔很小(OS 处理速度)。
**应该 work**,但有些应用会错过短暂的修饰键。

### 4.3 改进:加 delay

```rust
inputs.push(make_key(VK_HOME.0, 0));
inputs.push(make_key(VK_HOME.0, KEYEVENTF_KEYUP.0));
// 微延迟,让 OS 处理 Home 完成
Sleep(10);

inputs.push(make_key(VK_SHIFT.0, 0));
// 微延迟,让 Shift 状态稳定
Sleep(10);
inputs.push(make_key(VK_END.0, 0));
inputs.push(make_key(VK_END.0, KEYEVENTF_KEYUP.0));
Sleep(10);
inputs.push(make_key(VK_SHIFT.0, KEYEVENTF_KEYUP.0));
```

但 SendInput 是 async,加 Sleep 可能让整批 events timing 错乱。

**更稳的做法**:用 SendMessage 或 PostThreadMessage(特定线程)代替 SendInput。但这是不同 API。

### 4.4 实际行为推断

Windows 修饰键检测:
- 大多数 Win32 Edit 控件:跟踪 VK_SHIFT 状态,任何 Shift state 都有效
- Chromium:跟踪 key event 序列,Shift+End 必须 Shift 在 End 之前(可任意 ms)

Plan 序列中 Shift↓ → End↓ 之间没有明显延迟,但都是 SendInput batch 内的 events,OS dispatch 时 Shift 已经 down。

**结论**:plan 的时序**应该 work**,但**没实测保证**。

### 4.5 备用:Alt+PrtScn 方法(更可靠)

Win32 Edit 控件有几个**永远 work** 的 select-all 方法:
- **Ctrl+NumPad 0** (caret + shift selection 起点)
- **F6**(切换焦点到 address bar)
- **Alt+D**(Windows Explorer address bar focus)

但这些是**浏览器特有**,WinUI 3 wrapped 不知道。

## 5. 🟡 A4 没考虑 dialog 不在前台的 fallback

### 5.1 问题

Plan 删除 SetForegroundWindow 后,如果 dialog 不在前台:
- SendInput events 去 Sigma FM
- dialog 完全没反应
- 用户 visual 上看不到变化

### 5.2 plan D8 提到"接受拼接 + Edge flag"

但 plan 没提供"dialog 不在前台"的具体行为。

### 5.3 建议:加 GetForegroundWindow check

```rust
fn try_send_path_via_sendinput(dialog_hwnd: u32, target_path: &str) -> bool {
    let hwnd = HWND(dialog_hwnd as *mut core::ffi::c_void);
    unsafe {
        // (新) 检查 dialog 是否在前台
        let current_fg = GetForegroundWindow();
        if current_fg != hwnd {
            warn!(
                "v0.5.3 SendInput: dialog hwnd={hwnd:?} is not foreground \
                 (current foreground: {current_fg:?}). Skipping SendInput — \
                 events would go to wrong window."
            );
            // 不调用 SendInput,返回 false 触发 H2 fallback
            return false;
        }
        
        // dialog 在前台,继续原 plan
        let mut inputs: Vec<INPUT> = Vec::with_capacity(8 + target_path.len() * 2);
        inputs.push(make_key(VK_CONTROL.0, 0));
        // ... Ctrl+L ...
        inputs.push(make_key(VK_HOME.0, 0));
        // ... Home + Shift+End + path ...
        
        let n = SendInputFn(&inputs, std::mem::size_of::<INPUT>() as i32);
        // ...
    }
}
```

这样:
- dialog 在前台 → SendInput 正常工作
- dialog 不在前台 → abort 触发 H2 fallback(SetValue + restore)
- 不会污染 Sigma FM 输入框

### 5.4 与"用户手动切回 dialog"工作流配合

用户场景:
1. Edge Save As dialog 打开
2. 用户切到 Sigma FM 导航
3. Sigma FM extension PUSH path
4. sidecar 收到 PUSH → 检查 dialog 在前台 → 不在 → abort + log "请手动切回 dialog"
5. 用户看到 dialog 没变化,手动点 dialog → foreground 切换
6. **此时下一个 PUSH** 才会工作

但这是**单次 PUSH 失败**,不是"持续失败"。

**改进**:PUSH 时缓存到 `pending_path` state, 当 extension 检测到 dialog foreground(下次 PUSH 时检查)就 apply。

**实施复杂度**:中等。这是真正的"用户主动切焦点"实现。

## 9. 完整修复方案 B1(推荐 — 保留 SetForegroundWindow)

### 9.1 完整 diff

```rust
fn try_send_path_via_sendinput(dialog_hwnd: u32, target_path: &str) -> bool {
    let hwnd = HWND(dialog_hwnd as *mut core::ffi::c_void);
    unsafe {
        // B1: 保留 AllowSetForegroundWindow + SetForegroundWindow
        // 它们通常 no-op,但在某些情况能让 dialog 在前台。
        // 不应被视为"焦点盗窃" — 用户期望 dialog 在前台才能 receive SendInput。
        let _ = AllowSetForegroundWindow(ASFW_ANY);
        let _ = SetForegroundWindow(hwnd);

        // B1 (新): 检查 dialog 是否真的在前台
        let current_fg = GetForegroundWindow();
        if current_fg != hwnd {
            warn!(
                "v0.5.3 SendInput: dialog is not foreground (current_fg={current_fg:?}); \
                 events may not reach dialog. User should manually focus dialog."
            );
            // 不 abort — 仍尝试 SendInput,有时 user 切回 dialog 时 events 已被 dispatch
        }

        let mut inputs: Vec<INPUT> =
            Vec::with_capacity(8 + target_path.encode_utf16().count() * 2);

        // Step 3: Ctrl+L — focus Chromium's address bar.
        inputs.push(make_key(VK_CONTROL.0, 0));
        inputs.push(make_key(VK_L.0, 0));
        inputs.push(make_key(VK_L.0, KEYEVENTF_KEYUP.0));
        inputs.push(make_key(VK_CONTROL.0, KEYEVENTF_KEYUP.0));

        // Step 3b: Home + Shift+End — basic Edit operations, WinUI 3 unlikely to intercept.
        inputs.push(make_key(VK_HOME.0, 0));
        inputs.push(make_key(VK_HOME.0, KEYEVENTF_KEYUP.0));
        inputs.push(make_key(VK_SHIFT.0, 0));
        inputs.push(make_key(VK_END.0, 0));
        inputs.push(make_key(VK_END.0, KEYEVENTF_KEYUP.0));
        inputs.push(make_key(VK_SHIFT.0, KEYEVENTF_KEYUP.0));

        // Step 4: type the path char-by-char (press + release per MSDN).
        for ch in target_path.encode_utf16() {
            inputs.push(make_unicode(ch));
            inputs.push(make_unicode_release(ch));
        }

        let n = SendInputFn(&inputs, std::mem::size_of::<INPUT>() as i32);
        let total = inputs.len() as u32;
        if n != total {
            warn!(
                "v0.5.3 SendInput: queued {total} events, system accepted only {n}"
            );
            return false;
        }
        info!(
            "v0.5.3 SendInput Ctrl+L + Home+Shift+End + path dispatched \
             ({total} events, no Enter)"
        );
        true
    }
}
```

### 9.2 Event count

| C:\evid (7 chars) | 8 + 14 = 22 |
| C:\downloads (12 chars) | 8 + 24 = 32 |

比 plan v0.5.3 (24 for C:\evid) 少 2 events (没有冗余 Ctrl↓,符合 v0.5.1 review MIFA 我建议)。

### 9.3 行为保证

- dialog 在前台:SendInput 全部工作 → address bar 替换 ✓
- dialog 不在前台:SendInput events 去 Sigma FM,但有 warn log 让用户知道
- 焦点:不动 SetForegroundWindow(no-op),保留默认行为

### 9.4 不引入新 bug

- 不删任何东西 → 不会破坏已有 work
- Home+Shift+End 是基本 Edit 操作,WinUI 3 不太可能 intercept
- GetForegroundWindow 是 read-only,无副作用

    unsafe {
