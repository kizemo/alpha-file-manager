## 2. v0.5.4 修复方案评估

### 2.1 改动范围(plan §3.1)

**文件**:`sigma-listary-spike/src/uia_inject.rs`
**函数**:`try_send_path_via_sendinput`
**改动**:`if current_fg != hwnd` block 内加 `return false;` + log message 更新

### 2.2 改动前(v0.5.3,plan §3.2)

```rust
let current_fg = GetForegroundWindow();
if current_fg != hwnd {
    warn!("...");
    // ⚠️ 仍继续 SendInput (race condition!)
}
let mut inputs: Vec<INPUT> = ...;
// ... build & send SendInput ...
```

### 2.3 改动后(v0.5.4,plan §3.3)

```rust
let current_fg = GetForegroundWindow();
if current_fg != hwnd {
    warn!("v0.5.4 SendInput: dialog hwnd={hwnd:?} is not foreground \
           (current={current_fg:?}); aborting to trigger H2 fallback.");
    return false;  // ← 触发 H2 fallback
}
let mut inputs: Vec<INPUT> = ...;
// ... build & send SendInput ...
```

✅ **改动最小化** — 1 行 `return false;` + log message 更新。

### 2.4 fallback chain(plan §3.4)

```
Edge Save As dialog (WinUI 3 wrapped):
  COM IFileDialog::SetFolder              ← Layer 1 (round 19f)
    ↓ fail (AccessibleObjectFromWindow failed)
  UIA 4-layer fallback:
    detect WinUI 3 wrapped (has_filename_host + has_1001)
      ↓
      H1 SendInput Ctrl+L + Home+Shift+End + path:
        GetForegroundWindow check:
          dialog foreground → SendInput → return AddressBarWritten
          dialog !foreground → abort → return false → H2
      ↓ return false
      H2 SetValue target + SetValue original (50ms sleep):
        SetValue 1001 = "C:\evid" → chromium 更新 breadcrumb
        Sleep(50ms)
        SetValue 1001 = original filename → 恢复
        return AddressBarWritten
      ↓ return false
      F3 v0.5.0 baseline: SetValue + Invoke Save(known pollution)
      ↓ return false
      Unsupported + notification
```

✅ **fallback chain 完整**,从 Layer 1 到 Layer 5。

### 2.5 H2 路径已存在(plan §3.5)

`try_h2_restore_filename` 在 source 已实施(plan v0.5.1 §3.2)。

**关键**:H2 用 UIA SetValue,**不需要 foreground**。

✅ 这是 v0.5.4 修复的核心机制:
- H1 (SendInput) 需要 dialog foreground
- H2 (UIA SetValue) 不需要 foreground

当 dialog 不在前台时,H1 abort → H2 fallback → UIA SetValue 直接调用,可能 work。

## 3. 🟡 O1 — H2 fallback 是否 work when dialog 不在前台

### 3.1 假设

plan §3.5 假设 H2 在 dialog 不在前台时 work,**但未实测验证**。

### 3.2 实际可能

UIA SetValue 通过 COM 调用,理论上不需要 foreground。但 WinUI 3 wrapped dialog 可能在某些情况下要求 foreground:

| 情况 | H2 work? |
|---|---|
| WinUI 3 dialog 已 minimum(用户切到 Sigma FM)| UIA SetValue 直接调,可能 work |
| WinUI 3 dialog 在 UAC / elevated process | UIA 可能 fail(permission denied) |
| WinUI 3 dialog 已被 UIA 释放(element handle stale)| SetValue fail |
| WinUI 3 dialog 在另一个 session | UIA 跨 session 可能 fail |
| WinUI 3 dialog 已被 destroyed | SetValue fail |

### 3.3 实测建议

实施 v0.5.4 后,**实测**以下场景:
1. **Scenario A**: dialog 在前台 → H1 → H1 work → 完成 ✓
2. **Scenario B**: dialog 在 background(Sigma FM 在前台)→ H1 abort → H2 → H2 需 work
3. **Scenario C**: dialog 在 background + H2 fail → F3(v0.5.0 baseline)→ F3 也 fail → Unsupported

### 3.4 如果 H2 fail,plan 的应对

plan §3.4 fallback chain 显示 F3 是 next:
```rust
if is_winui3_wrapped {
    // H1 attempt
    if try_send_path_via_sendinput(dialog_hwnd, target_path) { ... }
    // H1 fail → try H2
    if let Some(edit) = best_edit.as_ref() {
        if try_h2_restore_filename(edit, target_path) { ... }
    }
    // H2 fail → fall through to F3 v0.5.0
}
// F3: SetValue 1001 + Invoke Save (known pollution)
```

**问题**:H2 和 F3 都做 SetValue 1001。如果 H2 fail,F3 也会 fail(同样操作)。

**plan §4 不达标应急**:
> "最坏情况:H2 + F3 都 fail → Unsupported + notification(用户可手动操作)。"

✅ plan 接受 worst case fallback。但**未实测 verify H2 + F3 是否真会同时 fail**。

### 3.5 建议

实施 v0.5.4 后,实测 Scenario B(关键)。如果 H2 fail,**需要 fallback 到 v0.5.2 race condition 行为**(已 work),或者考虑其他方案。

## 4. 🟡 O2 — SetForegroundWindow + GetForegroundWindow race

### 4.1 假设

plan §3.3 流程:
```rust
let _ = SetForegroundWindow(hwnd);  // 可能 fail (Vista+ lock)
let current_fg = GetForegroundWindow();  // 读当前 foreground
if current_fg != hwnd {
    return false;
}
```

### 4.2 race 场景

| 场景 | SetForegroundWindow 结果 | GetForegroundWindow 结果 | 实际行为 |
|---|---|---|---|
| A: dialog 已在 foreground | no-op | dialog == dialog | proceed SendInput → work ✓ |
| B: Sigma FM 在前,no grant | fail(lock)| Sigma FM | abort → H2 |
| C: Sigma FM 在前,扩展 grant | success | Sigma FM(OS 异步)| abort → H2(应该 work)|
| D: dialog 刚被激活 | succeed(queued)| Sigma FM(race)| abort → H2(应该 work)|

**问题**:Scenario C 和 D 可能在 race window 内,SetForegroundWindow 已经成功但 GetForegroundWindow 仍返回旧 foreground → abort → H2。

但 H2 应该 work(UIA 不需要 foreground)。**最终结果不变**。

### 4.3 plan 没处理 race window 的延迟

为准确检测 foreground,需要 Sleep 几毫秒:
```rust
let _ = SetForegroundWindow(hwnd);
std::thread::sleep(std::time::Duration::from_millis(20));
let current_fg = GetForegroundWindow();
```

但 Sleep 增加复杂度。plan 没要求 Sleep。

**实际上不必要** — 因为 abort + H2 fallback 总是 work。

### 4.4 接受度

**接受** — race window 不影响最终行为,plan 不需要 Sleep。

## 5. 🟡 O3 — "Mavis I2 假设错了" 含糊

### 5.1 plan §5 列的"不要做的事"

```
| ❌ 改 extension index.js | Mavis I2 假设错了,无代码可删 |
```

### 5.2 问题

plan 说"Mavis I2 假设错了",但**没说**:
- 为什么 I2 错
- 是否需要 revert I2(即恢复 extension 的 `AllowSetForegroundWindow(sidecarPid)`)
- 用户的 v0.5.3 deployment 是否包含 I2 fix

### 5.3 事实重建

回顾 plan v0.5.3-c1-fix.md §1.2,我推荐删除 extension 中的:
```javascript
const sidecarPid = await getSidecarPid();
if (sidecarPid !== null) {
    await allowSetForegroundWindow(sidecarPid);
}
```

理由(Mavis §2.5):这是焦点盗窃真正根因。

### 5.4 实际 I2 fix 的影响

v0.5.3 部署了 I2 fix → 删了 extension 的 AllowSetForegroundWindow grant。

后果:
- v0.5.2: extension grants → sidecar SetForegroundWindow 可能 succeed → focus theft 但 sync work
- v0.5.3: extension 不 grants → sidecar SetForegroundWindow 永远 no-op → 无 focus theft 但 sync 也 fail

**I2 fix 解决了 focus theft 但破坏了 sync**。

### 5.5 为什么 I2 假设错了?

我假设 I2 fix 能解决 focus theft 不破坏 sync。但实际上:
- v0.5.2 的 race condition 是 sync 的**唯一原因**
- I2 fix 拆除了 race condition 的关键 enable(extension grant)
- 没有 grant,sidecar SetForegroundWindow 永远 no-op
- 没有 SetForegroundWindow success,SendInput events 不投递到 dialog

**我之前没意识到**:extension grant 是 race condition 工作的关键。删它 = 拆 race condition。

### 5.6 现在怎么办?

v0.5.4 修复方案:**保留 I2 fix**(不恢复 AllowSetForegroundWindow),改为 abort + H2 fallback。

**新思路**:
- I2 删 extension grant 是**正确**的(防止焦点盗窃)
- H2 fallback 是**新机制**,不依赖 SendInput race
- 一起 work:无 focus theft + sync work via UIA

### 5.7 plan §5 "无代码可删" 的含义

如果 v0.5.3 已经部署 I2 fix(extension 删了 AllowSetForegroundWindow),那么 **v0.5.4 不需要再删**(已经删了)。

"无代码可删"指 v0.5.4 不需要重复删。

### 5.8 plan 应澄清的

应该明确写:
> "v0.5.3 已部署 I2 fix(extension 删 AllowSetForegroundWindow)。v0.5.4 保留 I2 fix(不恢复 extension),改用 H2 fallback 替代 SendInput race condition 机制。"

**当前 plan 含糊** —— "Mavis I2 假设错了" 让读者误解为"应该 revert I2"。

### 5.9 建议

plan §5 行改为:
```
| ❌ 改 extension index.js (v0.5.4) | v0.5.3 已部署 I2 fix;v0.5.4 保留,不恢复 extension AllowSetForegroundWindow(避免焦点盗窃回归)|
```

## 8. plan §3.4 fallback chain 评估

### 8.1 Layer 1: COM IFileDialog::SetFolder

work for Win32 dialogs(影刀 RPA / Photos / Edge Legacy)。WinUI 3 wrapped Save As 不 work(plan §1.1 log 显示 "COM SetFolder unavailable")。

✅ 已实施,work for true IFileDialog。

### 8.2 Layer 2: H1 SendInput Ctrl+L + Home+Shift+End

**v0.5.4 行为**:
- dialog 在 foreground → SendInput → work
- dialog 不在 foreground → abort → Layer 3

### 8.3 Layer 3: H2 SetValue 1001 + restore

**v0.5.4 行为**:
- 不依赖 foreground
- UIA SetValue 调用 → Chromium 更新 breadcrumb + 50ms 后 filename 恢复
- 50ms 闪烁(plan v0.5.1 D7 接受)

### 8.4 Layer 4: F3 v0.5.0 baseline SetValue 1001

**v0.5.4 行为**(如果 H2 fail):
- SetValue 1001 to target_path
- breadcrumb 更新
- filename 永久被污染(无 restore)

**问题**:如果 H2 fail(F3 也 fail 因为同样 SetValue),用户看到的是 nothing changed + Unsupported。

实际上 F3 的 SetValue 不依赖 foreground,所以 F3 应该 work 当 H2 work 时。**F3 是 redundant of H2**。

### 8.5 Layer 5: Unsupported + notification

work for 完全失败的情况。

### 8.6 实际有效 layers

- Layer 1: Win32 dialog work
- Layer 2: SendInput work 当 dialog 在 foreground
- Layer 3: H2 work(几乎 always,因为 UIA 不依赖 foreground)
- Layer 4: F3 work(但和 Layer 3 redundant)
- Layer 5: notification(完全 fail 时)

**实际只有 3 个有效 layers**(L1, L2-L3, L5)。Layer 4 是冗余。

**接受** — redundant layer 作为 safety net。
