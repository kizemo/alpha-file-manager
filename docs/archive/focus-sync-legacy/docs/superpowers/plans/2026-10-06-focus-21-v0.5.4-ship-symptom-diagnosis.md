### 2.3 关键证据 3 — v0.5.4 fix 代码确认(`uia_inject.rs:239-265`)

```rust
fn try_send_path_via_sendinput(dialog_hwnd: u32, target_path: &str) -> bool {
    let hwnd = HWND(dialog_hwnd as *mut core::ffi::c_void);
    unsafe {
        let _ = AllowSetForegroundWindow(ASFW_ANY);
        let _ = SetForegroundWindow(hwnd);

        // v0.5.4 (2026-10-06 复盘): MUST abort instead of silent continue.
        // Per Mavis review §1.3: SendInput events dispatch to the
        // foreground window (possibly NOT dialog). Without abort + H2
        // fallback, dialog never receives the path and user sees
        // "completely no response". Abort returns false → inject_via_uia
        // falls through to H2 (UIA SetValue, no foreground dependency).
        let current_fg = GetForegroundWindow();
        if current_fg != hwnd {
            warn!(
                "v0.5.4 SendInput: dialog hwnd={hwnd:?} is not foreground \
                 (current={current_fg:?}); aborting to trigger H2 fallback."
            );
            return false;  // ← v0.5.4 fix 正确部署
        }
        // ...
    }
}
```

### 2.4 关键证据 4 — 策略 dispatch 路径(`uia_inject.rs:548-668`)

`inject_via_uia()` 调用顺序:
1. 扫描 dialog 的 UIA 元素 → 计算 `is_winui3_wrapped_signature`
2. `is_winui3_wrapped` = true → 走 4 层 fallback(H1 → H2 → F3)
3. `is_winui3_wrapped` = false → 直接走 F3 baseline SetValue 1001
4. 全部走完后 `Ok(())` → `inject_folder_path` 返回 `DialogOutcome::AddressBarWritten`
5. `AddressBarWritten → WriteOutcome::UiaSetValue`(writer.rs:78)
6. 日志: `strategy: "uia"`

**关键观察**:
- spike.log 中所有 Write 都是 `strategy="uia"` —— 表示走的是 UIA 路径(`AddressBarWritten`),**不是** `strategy="sendinput"`(意味着 H1 SendInput **从未成功返回**)
- dialog class 是 `#32770`(legacy IFileDialog),不是 WinUI 3 wrapped,**走 F3 baseline 而不是 H1**
- v0.5.4 修复只对 WinUI 3 wrapped dialog 的 H1 路径生效 —— **本次实测触发不到是预期行为**

### 2.5 关键证据 5 — extension PUSH 实现(`release/extension/dist/index.js:559-569`)

```js
try {
    sigma.context.onPathChange((path) => {
        console.log('[focus-sync] onPathChange raw=' + JSON.stringify(path));
        if (path) schedulePush(path);
    });
} catch (e) {}  // ← 静默吞错

try {
    const initialPath = await sigma.context.getCurrentPath();
    if (initialPath) schedulePush(normalizePath(initialPath));
} catch (e) {}
```

**关键观察**:
- `sigma.context.onPathChange` 是 Sigma FM 的 extension API,**不在 sidecar 代码控制范围内**
- 错误被 `try/catch(e) {}` 静默吞掉 —— 即使 extension 注册失败,日志也不会有错误
- PUSH 的触发完全依赖 Sigma FM 的 `onPathChange` event firing

## 4. Phase 3 — 单一假设 + 最小化测试

### 4.1 两个假设

#### 假设 H1(Sigma FM extension 未触发 PUSH)

- **唯一合理解释 symptom B**:spike.log 显示 0 个 `path_update` 来自 extension
- **可能原因**:
  - H1.a Sigma FM init TDZ 错误阻断 extension API → `sigma.context.onPathChange` 不 fire
  - H1.b Sigma FM 多个实例冲突(HotKey `Super+Shift+E` already registered)→ extension host 状态错乱
  - H1.c Extension manifest 加载失败 → `activate()` 异常退出
- **可测试**:Sigma FM DevTools Console filter `[focus-sync]`,导航 C:\downloads,看是否输出 `onPathChange raw=...`

#### 假设 H2(Chromium 41477 element UIA SetValue append)

- **合理解释 symptom A**:spike.log 看到 `target="C:\\" strategy="uia"` 但用户看到的是 append 而非 replace
- **代码依据**:`filename_edit_score` 函数给 `automation_id == "41477"`(Chromium address bar)打 95 分,**高于** `automation_id == "1001"`(legacy filename)的 90 分
- **可能原因**:Chromium 41477 是 ComboBox 类型,UIA SetValue 调用行为在 Chromium 实现中可能 append 到 .Value 字符串而非 .Edit.Value
- **可测试**:用 UI Automation Inspector(微软斧子官斧工具)或 Accessibility Insights扫描 dialog,看 best_edit 是 41477 还是 1001,然后单独测 SetValue 行为

### 4.2 验证优先级

| 假设 | 验证成本 | 信息价值 | 优先级 |
|---|---|---|---|
| H1(extension 未触发 PUSH) | 低(打开 Sigma FM DevTools filter 即可) | 高(直接验证 symptom B) | **P0** |
| H2(41477 SetValue append) | 中(需要 UIA Inspector + 手动触发 Save As) | 高(直接验证 symptom A) | **P1** |

## 5. Phase 4 — 建议实施步骤

### 5.1 不修 v0.5.4 —— 修复正确,不需改动

v0.5.4 的 1 行 `return false;` 修复是 sound 的(基于真实 spike.log 证据),binary 部署正确。本次实测不触发是因为 dialog class 不在范围内。等 WinUI 3 wrapped dialog 真正出现时,该修复会发挥预期作用。

### 5.2 诊断步骤(不写代码,只收集证据)

#### Step 1 — 验证 extension 是否 PUSH(P0,~30 秒)

1. 打开 Sigma FM DevTools(已经是打开状态,根据 screenshot)
2. Console filter 输入 `[focus-sync]`
3. 导航到 C:\downloads
4. **观察**:
   - 是否出现 `onPathChange raw="..."` 日志?—— **否 = 假设 H1.a 确认**
   - 是否出现 `PUSH response status=200`?—— **否 = 假设 H1.b/c 确认**
6. **如果没有任何 focus-sync 日志** → extension 没 activate 或 PUSH 触发器坏了,**完全不在 sidecar 责任范围**

#### Step 2 — 验证 dialog UIA tree(P1,~5 分钟)

1. 下载并运行 **Accessibility Insights** 或 **UI Automation Inspector**
2. 触发 Edge Save As dialog(filename 任意)
3. 扫描 dialog 的 UIA tree
4. **观察**:
   - best_edit(评分最高 Edit 元素)的 `automation_id` 是 1001 / 1148 / 41477?
   - 41477 element 的 `Value` vs `Edit.Value` 字段分别是什么?
6. **手动调用 SetValue("C:\\")** 看是 replace 还是 append

### 5.3 修复分支(根据 Step 1/2 结果)

#### 如果 H1 确认(extension 没 PUSH)

- **不在 v0.5.4+ sidecar 范围**
- 需要回到 Sigma FM 主项目排查 extension host / `sigma.context` API / navigator module
- 可能方案:
    - 检查 Sigma FM 是否需要重启(看 HotKey 冲突是否解决)
    - 检查 extension manifest 在 `release/extension/dist/` 是否完整
    - 看 Sigma FM issue tracker 有没有同类 TDZ 报告

#### 如果 H2 确认(41477 SetValue append)

- **在 v0.5.5+ 范围**(新工作)
- 可能方案:
    - **方案 A**:在 `filename_edit_score` 里把 41477 分数从 95 降到 50(低于 1001 的 90),让 best_edit 落到 filename 而不是 address bar
    - **方案 B**:对 Chromium dialog 显式优先选 1001(filename)而不是 41477(address bar)
    - **方案 C**:F3 baseline 之前,对 Chromium 41477 element 先 SetValue("")(清空)再 SetValue(target),避免 append
    - **方案 D**:走 H1 SendInput 路径(即使不是 WinUI 3 wrapped),Ctrl+L + Home+Shift+End + type 替代 SetValue
- **TDD 要求**:先写自动化测试,用 UIA mock 模拟 41477 element,验证 SetValue 行为
