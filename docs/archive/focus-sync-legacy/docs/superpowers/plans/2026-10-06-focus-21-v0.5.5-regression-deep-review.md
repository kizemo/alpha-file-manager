## 0. 一句话结论

**是计划问题,不是执行问题。执行是忠实的。**

v0.5.5 的代码 100% 按计划实施(binary probe + 源码双向验证)。计划本身有一个**根本性的设计错误**:

> 我们把"不要污染地址栏"当成了优化目标,把它做成了一个**硬门禁**;
> 而真正的主目标"能同步"在门禁后面,**一旦上游 extension 失效,门禁把唯一的兜底路径也一起关掉了**。

结果:从"脏但能动"退化成"干净但不动"。用户看到的就是**完全退步**。

**这是一个真实用户 dialog(`11.politics`,`#32770`),被 `should_opened_write_back` 拒绝写入。**

### 2.2 三行代码的执行推演

```rust
// state.rs:131-135
```

`current_path = ""`(Fix F 的 `default_value = ""`)
`first_push_received = false`(extension 从未 PUSH)

**→ 返回 false → 完全不写 → 用户看到零动作**

### 2.3 为什么 `first_push_received` 永远是 false

`state.rs:112` 只在 `set_current_path()` 里 mark。而 `set_current_path` 只在 `/set_path` handler 里被调用。

`/set_path` 只在 extension PUSH 时调用。

**extension PUSH 为什么不来?** 你截图里的错误:

```
ReferenceError: Cannot access 'U' before initialization
  at c (navigator-DJVMws3e.js:2:37962)
  at er (runtime-core.esm-bundler-Cz0gXyD0.js:1:23273)
```

`navigator-DJVMws3e.js` 是 **Sigma FM 自己的模块**,`runtime-core.esm-bundler` 是 **Vue 3 runtime**。这是 Sigma FM 主项目的 TDZ 错误,发生在 `index-w9EUyM0-.js` 的 `background:*` 任务链里(`restoreStartupTabs` / `terminals.init` / `globalSearch.initOnLaunch` / `appUpdater.initAutoCheck`)。

**Sigma FM 的 extension host 被这个错误打断 → `sigma.context.onPathChange` 注册失败或回调不 fire → PUSH 永远不来。**

## 3. 退步的本质:两个目标的优先级被搞反了

| 时间点 | 触发条件 | 写入行为 | 用户体验 |
|---|---|---|---|
| **v0.5.4** | extension 坏 | 写 `C:\`(sentinel)到 dialog | **"动了一下"**,地址栏被污染,但用户说"有可能同步到地址栏、文件名处" |
| **v0.5.5** | extension 坏 | **完全不写** | **"完全没有同步动作"** |

**这是一个 trade-off,但我做了一个错误的判断。**

我在 v0.5.5 review 里写的核心论据是:

> "Fix B guard 一次性修复了污染源头…… 即使 PUSH 永远不来,sidecar 也不污染 dialog"
> "**sidecar 100% 正确也 sync 不了**(Symptom B 在 Sigma FM 主项目)"

这句话是对的。**但我从这句话推出"所以不写是可接受的"——这是错的。**

用户的诉求从来不是"不污染",而是**"能同步"**。

当二者冲突时:
- 用户明确说过:**"dialog 真正跳转 + 不要把路径写进 filename 字段"**
- v0.5.4 的"污染"至少是**部分成功**(导航到了某个位置)
- v0.5.5 的"不写"是**100% 失败**

**把"部分成功"换成"全部失败",在用户眼里就是退步。这是我的判断错误,不是实现错误。**

## 5. v0.5.6 修正方案

### 5.1 设计原则(先立规矩,再改代码)

**任何 gate 必须回答:gate 之后还剩什么可用路径?**

如果答案是"什么都不剩",这个 gate 就是**功能删除**,不是优化。

### 5.2 修正 1:`should_opened_write_back` 加 fallback(核心)

```rust
// state.rs:131
pub fn should_opened_write_back(&self, initial_path: &str, current_path: &str) -> bool {
    if initial_path.is_empty() || initial_path == current_path {
        return false;                       // 无意义的写,跳过
    }

    if self.has_first_push_received() {
        return true;                        // 正常路径:写用户真实路径
    }

    // ── v0.5.6 fallback(Mavis Round 27 修正)──────────────────────────
    // extension 尚未 PUSH(first_push_received == false)时,
    // 仍然执行写入,保持 v0.5.4 的兜底能力。
    //
    // 为什么不 gate:
    //   extension PUSH 依赖 Sigma FM 的 sigma.context.onPathChange,
    //   该 API 在 Sigma FM Vue runtime 报错时不会 fire(v0.5.5 实测)。
    //   若此处 gate,唯一的兜底写入路径被关闭,功能 100% 失效。
    //
    // 为什么 v0.5.4 写 sentinel 可接受:
    //   current_path 初始为 "C:\\"(Fix F 退回),是用户当前真实路径的
    //   合理近似 —— 总比完全不写好。
    //   v0.5.5 的 default_value="" 让 fallback 无内容可写,
    //   这是 Fix F 与 Fix B 的共谋,必须一起退回。
    // ─────────────────────────────────────────────────────────────────
    true
}
```

**配合 Fix F 退回**:

```rust
// main.rs:30
#[arg(long, default_value = "C:\\")]   // v0.5.6: 退回 sentinel
initial_path: String,
```

**两者必须一起改**,否则 fallback 写了空字符串。

### 5.3 修正 2:污染问题改用"写对元素"而非"不写"

真正的污染根因是 **Fix A(41477 评分错误)**,它已经在 v0.5.5 修好了。

v0.5.5 的 binary probe 显示 `v0.5.5 SendInput` = 5(Fix H 生效)、`first_push_received` = 1(Fix E 生效),**Fix A 的 `continue` 过滤也落地了**。

所以 v0.5.6 的 fallback 写入会走到**正确的元素(1001/1148)**,而不是 41477。

**Fix A 解决"写错地方",fallback 解决"不写"。两者不冲突。**

### 5.4 修正 3:扩展通知机制(Fix E 的价值兑现)

Fix E 已经在 `/health` 暴露了 `first_push_received`。v0.5.6 应该**真正使用它**:

```rust
// main.rs:409 附近
} else if !initial_path.is_empty() && initial_path != current {
    log_event(&Event::SpikeError {
        kind: "opened_write_back_fallback".into(),   // 改名:不再是 skip
        message: format!(
            "dialog path='{}' current='{}' (fallback: extension not yet PUSH, \
             writing sentinel to preserve v0.5.4 behavior)",
            initial_path, current
        ),
        ts: now_iso8601(),
    });
}
```

日志 event 名从 `opened_write_back_skip_sentinel` 改为 `opened_write_back_fallback` —— 让运维/用户能区分"跳过"和"降级写入"。

### 5.5 修正 4:把 Fix E 变成真正的预警

扩展应该读 `/health` 的 `first_push_received`,若为 false 且 `active_dialogs > 0`,显示:

> ⚠️ Sigma FM 未推送路径,当前使用降级模式(写入 C:\)

这样用户能**看到降级状态**,而不是困惑于"为什么地址栏不对"。

## 6. 100+ 轮原地踏步的机制分析

### 6.1 六轮 review 的关注点漂移

| 轮次 | 我关注 | 找到 | 是否触及"功能失效" |
|---|---|---|---|
| R22 | unit test 可编译性、helper 存在性 | R-1~R-4 | ❌ |
| R23 | 版本号 bump、老 test 兼容、extension 字符串 | N-1~N-5 | ❌ |
| R24 | 周边文件、注释、算术 | P-1~P-4 | ❌ |
| R25 | binary 工具链假设、Fix 副作用 | Q-1~Q-5 | ❌ |
| R26 | `continue` 语义、版本号耦合 | S-1~S-4 | ❌ |
| **R27(本轮)** | **功能是否还在** | **规则 55** | ✅ |

**每一轮都在"更深的细节"上打转,没有一轮问"功能整体还能不能用"。**

### 6.2 三个结构性缺陷

**缺陷 1:验证只看"改动是否生效",不看"功能是否可用"**

- U-V26b:`grep "v0.5.5 SendInput"` = 5 ✅ —— 改动生效了
- 但没有任何一个 U-V 是"用户能同步到路径"
- **"改动生效" ≠ "功能可用"**

**缺陷 2:每个 Fix 单独审查,没有审查 Fix 之间的交互**

- Fix B(`first_push_received` gate):单独看,防止 sentinel 污染,合理
- Fix F(`default_value = ""`):单独看,消除 sentinel,合理
- **但 B + F 组合 = 唯一兜底路径失效**
- Claude 复盘的 M-2 精准指出了这点,但这应该是我 R22 就发现的

**缺陷 3:把"已知必然发生的失败"当成了"边缘情况"**

`spike.log` 从 06:40 起就是 **0 个 extension PUSH**。v0.5.4 复盘(Round 21/22)已经明确写了:

> "extension 是完全没有触发 PUSH"
> "sidecar 100% 正确也 sync 不了 PUSH 永远不来"

**我在写 v0.5.5 计划时,明知上游必然失效,却在一个必然失效的上游上加了硬门禁。** 这是最核心的错误。

### 6.3 为什么没早发现

因为我把"不污染"当成了可交付价值,却没有问:**"污染但能动" 和 "干净但不动",用户选哪个?"**

答案用户已经给过:"**之前有可能同步到地址栏、文件名处**"——他在怀念 v0.5.4 的"能动"。

**我优化了一个用户没有要求的维度,牺牲了用户唯一要求的维度。**

## 7. 沉淀规则

### 规则 55(采纳 Claude 建议 + 我的深化)

```markdown
### 规则 55 — 任何 gate 必须回答"gate 之后还剩什么"

**触发**:v0.5.5 退步事件(2026-10-06)

**事件**:
Fix B(first_push_received gate)+ Fix F(default_value="")组合,
关闭了 opened_write_back —— 唯一的兜底写入路径。
extension PUSH 因 Sigma FM Vue runtime TDZ 错误不来
→ first_push_received 永远 false
→ should_opened_write_back 永远 false
→ 零写入。用户从"部分同步"退化为"完全无同步"。

**规则**:
1. 任何 gate/守卫/条件判断,实施前必须回答:
   "如果这个 gate 永远不通过,系统还剩什么可用路径?"
   如果答案是"什么都不剩",这个 gate 是**功能删除**,不是优化。
2. gate 一个 fallback 路径之前,必须确认至少还有另一条兜底。
3. "已知必然失败的上游"(如 extension PUSH 已实证失效)不能被
   硬门禁依赖 —— 门禁在此处等于功能删除。
4. 优化"不污染"类次要维度时,不得牺牲"功能可用"这个主维度。
   用户诉求优先级:能同步 > 同步位置正确 > 不污染。
5. 单点审查不够 —— 必须审查 Fix 之间的交互效应(B + F 共谋)。
```

### 规则 56(新增,来自本轮)

```markdown
### 规则 56 — "改动生效" U-V 不等于 "功能可用" U-V

**触发**:v0.5.5 全部 U-V 通过(binary probe 全中),
但用户实测零同步。

**规则**:
1. 每轮 ship 前必须有至少 1 个端到端功能 U-V,
   而不是全部由 grep / binary probe / unit test 组成。
2. 功能 U-V 的标准:用户可见的行为改变
   (如"地址栏显示 C:\downloads"),不是"代码里有这段字符串"。
3. 若无法做端到端验证,必须明说"本次 ship 未验证功能可用性",
   而不能因为"所有技术 U-V 都通过"就宣称 ship-ready。
4. 优先级:功能 U-V > 回归 U-V > 实现 U-V(binary/source grep)。
```
