## 1. Q-1(CRITICAL):U-V20 / U-V21 永远失败 — 实测证据

### 1.1 问题

v4 §7.1(沿用 v3/v2,最初**由我在 Round 22 §7 提出**):

| U-V | 任务 | 期望 |
|---|---|---|
| U-V20 | `grep binary for "v0.5.5" + "Do NOT revert"` | 都找到 |
| U-V21 | `grep binary for "compute_score_for_automation_id"` | 找到 |

### 1.2 实测:对当前 release binary 做字节级 probe

```
$ spike.exe (2,792,960 B, v0.5.4, strip=true, lto=thin)
compute_score_for_automation_id     -> 0
filename_edit_score                 -> 0
Do NOT revert                       -> 0
v0.5.4 SendInput                    -> 1
0.5.4                               -> 2
v0.5.3 SendInput                    -> 4
GetForegroundWindow                 -> 1
```

**结论**:
- `"Do NOT revert"` = **Rust 注释** → 编译器直接丢弃 → 永不进 binary → U-V20 **必然 fail**
- `compute_score_for_automation_id` = **函数名符号** → `Cargo.toml [profile.release] strip = true` + `lto = "thin"` 剥离 → 永不进 binary → U-V21 **必然 fail**
- `v0.5.4 SendInput` / `v0.5.3 SendInput` = **字符串字面量** → 进 `.rdata` → 能找到(1 + 4 = **正好 5 处**,与 Fix H 列的 5 处 runtime log 完全吻合)

### 1.3 根因

`sigma-listary-spike/Cargo.toml`:
```toml
[profile.release]
opt-opt = 3
lto = "thin"
codegen-units = 1
strip = true          # ← 符号全部剥离
```

Rust 的 release 构建中:
- **注释**永远不进 binary(与 strip 无关)
- **函数名/符号名**在 `strip = true` 下剥离
- **只有字符串字面量 + 常量值**进 binary

**这是我 Round 22 review 的错误建议**,被 v2 → v3 → v4 一路继承下来,从未被实测证伪。**必须修正。**

### 1.4 修正方案

## 2. Q-2(HIGH):Fix A 会让 Chromium-only dialog 从"成功"变 `WriteFailed`

### 2.1 机制

`uia_inject.rs:566` + `:594`:
```rust
let mut best_edit_score = i32::MIN;     // 初值 i32::MIN
...
let score = filename_edit_score(&element);
if score > best_edit_score {            // 严格大于
    best_edit_score = score;
    best_edit = Some(element);
}
```

Fix A 后,41477 返回 `i32::MIN`。若 dialog 的**唯一** Edit 元素是 41477:
- `i32::MIN > i32::MIN` = **false** → `best_edit` 保持 `None`
- `uia_inject.rs:651`:`let edit = best_edit.ok_or_else(|| Error::from(E_FAIL))?;` → **返回 Err**
- `writer.rs` → `WriteOutcome::Failed("unsupported_dialog_type")`

### 2.2 实证:这已经在发生

`spike.log` 已有 3 条 `WriteFailed reason:"unsupported_dialog_type"`:
```
04:25:31  hwnd=526354    path="bai"
05:11:37  hwnd=10752486  path="BFAOOE-AI-15"
06:49:39  hwnd=658330    path=".agents"
```

这些 dialog 打开时 filename 是 `bai` / `BFAOOE-AI-15` / `.agents`(像文件夹/无扩展名的路径),很可能是**只有 41477 没有 1001 的 Chromium-only dialog**。Fix A 会让**更多**这类 dialog 落到 `unsupported_dialog_type`。

### 2.3 影响评估

| 场景 | Fix A 前(v0.5.4) | Fix A 后(v0.5.5) |
|---|---|---|
| dialog 有 1001 + 41477 | 写到 41477 → **污染地址栏** ❌ | 写到 1001 → **正确导航** ✅ |
| dialog 只有 41477 | 写到 41477 → 污染地址栏(至少"动了") ⚠️ | `WriteFailed unsupported_dialog_type` ⚠️ |
| dialog 有 1148 | 正确 ✅ | 正确 ✅ |
| dialog 有 1001 only | 正确 ✅ | 正确 ✅ |

**这是 trade-off,不是纯 bug**:污染地址栏比明确失败更糟。但 v4 §8.1 风险表**没有列这一条**,U-V 矩阵也没有对应的验证项。

### 2.4 修正建议

**§8.1 风险表新增**:

| Risk | 影响 | 概率 | 缓解 |
|---|---|---|---|
| **Fix A 使 Chromium-only dialog 从 WriteFailed 升级** | 该类 dialog sync 完全失效(v0.5.4 至少污染了地址栏) | Medium | U-V27 实测:开一个只有 41477 的 dialog(无 1001),确认返回 `unsupported_dialog_type` 而非污染 |

**§7 新增 U-V27**:
| # | 任务 | 期望 |
|---|---|---|
| U-V27 | 在 Sigma FM 里开"新建文件夹"类 dialog(通常只有地址栏无 filename Edit),触发 write | `spike.log` 出现 `WriteFailed reason:"unsupported_dialog_type"`,**而不是**地址栏被写入。确认这是**预期行为**(明确失败优于静默污染) |

**并且**:`/health` 的 `unsupported_dialog_count` 会因此上涨。extension 的通知逻辑(基于此 counter)会开始弹通知 —— 用户会看到"这个 dialog 不支持"。这是**预期**的,但需要让用户知道这是 Fix A 的正常结果,不是新 bug。

## 4. Q-4(LOW):`i32::MIN` 哨兵与 `best_edit_score` 初值撞车

### 4.1 问题

`best_edit_score` 初值 = `i32::MIN`(`:566`),`filename_edit_score` 对 41477 返回 `i32::MIN`(Fix A)。

二者同值,靠**严格大于** `score > best_edit_score` 才没选中 41477。功能正确,但语义脆弱:
- 如果将来有人把比较改成 `>=`,41477 会立刻被选中
- 如果将来有人把初值改成 `i32::MIN + 1`(常见写法),41477 反而会赢

### 4.2 修正建议(更稳的写法)

**方案 A(推荐,v4 已有的 refactor 正好支持)**:让 `compute_score_for_automation_id` 对 41477 返回 `None`,**根本不参与打分**:

```rust
fn compute_score_for_automation_id(automation_id: &str) -> Option<i32> {
    if automation_id == "1148" { return Some(100); }
    if automation_id == "1001" { return Some(90); }
    // v0.5.5: 41477 是 Chromium 地址栏 ComboBox,SetValue 是 APPEND 不是
    // replace,写进去会污染地址栏。返回 None = 彻底不参与 best_edit 竞争。
    if automation_id == "41477" { return None; }
    None  // 未识别 id 也返回 None,落到 name 匹配
}

fn filename_edit_score(element: &IUIAutomationElement) -> i32 {
    let aid = current_automation_id(element);
    if aid == "41477" {
        return i32::MIN;   // ← 仍需一个"永不可选"值
    }
    ...
}
```

嗯,这样绕回来了。更干净的方案是**在调用点过滤**:

```rust
// uia_inject.rs:592 附近
if control_type == UIA_EditControlTypeId {
    // v0.5.5 (P-1 / Q-4): 41477 是 Chromium 地址栏 ComboBox,
    // UIA ValuePattern SetValue 是 APPEND 不是 replace — 写进去会污染
    // 地址栏("<current>C:\")而不是导航。彻底排除出 best_edit 候选。
    if current_automation_id(&element) == "41477" {
        continue;   // ← 不参与打分,语义清晰,不依赖 MIN 哨兵
    }
    let score = filename_edit_score(&element);
    if score > best_edit_score {
        best_edit_score = score;
        best_edit = Some(element);
    }
}
```

**优点**:
- 41477 不进竞争,`i32::MIN` 哨兵不再需要
- `filename_edit_score` 保持纯打分函数,可单测
- 只有 41477 的 dialog → `best_edit = None` → `WriteFailed`,**与 Q-2 行为一致但代码意图明确**

**但**:`continue` 会跳过该元素的 button 判定(`else if control_type == UIA_ButtonControlTypeId`)。41477 是 Edit 不是 Button,所以 `continue` 安全。但实施时要注意。

**如果不想改 `:592`**,至少在 v4 §5.1 的注释里加一句"依赖 `>` 严格大于;若改 `>=` 会回归"。

## 5. Q-5(LOW):Fix I extension 版本 `0.3.0 → 0.5.5` 跨 minor 跳

### 5.1 问题

`package.json:4` 从 `0.3.0` 直接跳到 `0.5.5`,跳过 0.3.x / 0.4.x / 0.5.0-0.5.4 全部。而 sidecar 的 0.4.x / 0.5.x 是**另一条 release train**(sidecar 版本)。

extension 与 sidecar 是两个独立产物:
- `SPIKE_VERSION`(http_server.rs)= sidecar binary 版本
- `package.json version` = Sigma FM extension 包版本

历史上 extension 停在 `0.3.0`(2026-09-30 Scheduled Task migration),而 sidecar 已到 `0.5.4`。说明两条 train 本来就是独立演进的。

### 5.2 建议

Fix I **建议不 bump**,或 bump 到 extension 自己的下一个小版本(如 `0.3.1`),而不是 `0.5.5`。

理由:
- extension 版本号语义 = "扩展本身的功能版本"
- sidecar 版本号语义 = "同步机制的版本"
- 把 sidecar 版本灌进 extension 版本会造成"extension 0.5.5 但功能还是 0.3.0 时代的"误导

**若决定 bump,建议 `0.3.0 → 0.3.1`**,并在 commit message 里说明"仅 bump extension 包版本以便 Sigma FM 识别新 dist"。
