## 1. S-1(HIGH,新引入):`continue` 跳过 `has_1001` 检测

### 1.1 v5 §5.1.1 的改法

v5 §5.1.1 建议在 `uia_inject.rs:592` 加:

```rust
if control_type == UIA_EditControlTypeId {
    if current_automation_id(&element) == "41477" {
        continue;            // ← Q-4 新增
    }
    let score = filename_edit_score(&element);
    if score > best_edit_score {
        best_edit_score = score;
        best_edit = Some(element);
    }
}
```

### 1.2 但 `has_1001` 检测在 `:588`,**在 `:592` 之前**

当前源码(`uia_inject.rs:588-604`):

```rust
588:        if aid == "1001" {
589:            has_1001 = true;              // ← WinUI 3 签名检测
590:        }
591:
592:        if control_type == UIA_EditControlTypeId {
593:            let score = filename_edit_score(&element);
...
```

`:573` 已经算出 `let aid = current_automation_id(&element);`。所以 `:588` 的 `if aid == "1001"` **对 41477 元素也是 false**(41477 ≠ 1001),`continue` 不会跳过 `:588` —— 因为 `:588` 在 `continue` 之前执行。

### 1.3 等等 —— 让我重新核对顺序

`:573` `let aid = ...` → `:581-587` FileNameControlHost 检测 → `:588-590` `has_1001` 检测 → `:592-604` best_edit/button 打分

`continue` 写在 `:592` 内部,**不影响** `:581-590` 的检测。

**所以 S-1 不成立。** 我需要更仔细地找真正的 bug。

### 1.4 真正的问题:`aid` 已在 `:573` 算出,`:592` 又调一次

v5 的 `continue` 用 `current_automation_id(&element)` 而不是复用 `:573` 的 `aid` 变量:

```rust
// :573 已有
let aid = current_automation_id(&element);

// :592 v5 新增
if current_automation_id(&element) == "41477" {   // ← 重复 UIA COM 调用
    continue;
}
```

`current_automation_id` 每次调用都做一次 COM 跨进程调用(`element.CurrentAutomationId()`)。dialog 元素多时(如 200 个元素)会**多出 200 次 COM 往返**。

**这是性能回归,不是正确性 bug。** UIA 跨进程 COM 调用通常 0.1-1ms,200 次 = 20-200ms。而 `inject_via_uia` 在 dialog 打开的关键路径上跑(main loop),会增加用户可感知的延迟。

**修正**(S-1 重新定义):

```rust
if control_type == UIA_EditControlTypeId {
    // v0.5.5 (Q-4): 41477 是 Chromium 地址栏 ComboBox,...
    // 复用 :573 已算出的 `aid`,避免重复 UIA COM 调用
    if aid == "41477" {
        continue;
    }
    let score = filename_edit_score(&element);
    ...
}
```

## 3. S-3(MEDIUM):Fix I 与 Fix G 版本号不一致

### 3.1 Fix I(v5 §5.10)

```json
"version": "0.3.1"    // package.json
```

### 3.2 Fix G(v5 §5.6,沿用 v3/v4)

`register.ps1` 10 处:
```powershell
version      = '0.5.5'      # line 87, 185, 222
latestVersion    = '0.5.5'  # line 226
if ($existingVersion -ne '0.5.5') {   # line 240
$json.installedExtensions.'kizemo.focus-sync'.version = '0.5.5'       # line 250
$json.installedExtensions.'kizemo.focus-sync'.manifest.version = '0.5.5'  # line 251
```

### 3.3 冲突

`register.ps1` 写的是 Sigma FM 的 extension 注册元数据(`installedExtensions.kizemo.focus-sync.version` = `0.5.5`),而 `package.json` 的 `"version"` 是 `0.3.1`。

Sigma FM 加载 extension 时:
- 可能读 `package.json` 的 `version`(npm 惯例)
- 可能读 `installedExtensions.*.manifest.version`(register.ps1 写的)

**如果两个都被读,用户会看到两个不同的版本号。**

### 3.4 我 Round 25 的 Q-5 判断需要修正

我建议 `0.3.0 → 0.3.1` 是基于"extension 与 sidecar 是独立 train"。但 **v2 以来 `register.ps1` 一直把 sidecar 版本号写进 extension 的 manifest.version**(`'0.5.3'` / `'0.5.4'`)。这说明**历史上这个项目就是把两者耦合的**。

所以 Q-5 的正确解法是**保持耦合**:
- `package.json` → `"0.5.5"`(与 register.ps1 一致)
- 承认 extension 和 sidecar 共用一个版本号(历史既定事实)

### 3.5 修正建议

**撤回 Q-5 / Fix I**,或者把 Fix I 改回 `0.5.5`:

| 方案 | package.json | register.ps1 | 一致? |
|---|---|---|---|
| **v4 原方案** | `0.5.5` | `0.5.5` | ✅ |
| **v5 方案(有 bug)** | `0.3.1` | `0.5.5` | ❌ |
| **v6 建议** | `0.5.5` | `0.5.5` | ✅ |

**我 Round 25 的 Q-5 判断是错的** —— 我以为两条 train 独立,但 `register.ps1` 的历史证明它们是耦合的。**认错并修正。**

## 4. S-4(LOW):U-V20b grep 精度

v5 §7.1:

| U-V20b | `grep "0.5.5" spike.exe` | ≥ 1 命中 |
|---|---|---|

### 4.1 问题

`grep "0.5.5"` 是子串匹配。如果 binary 里有 `0.5.50` / `0.5.55` / `10.5.5`,都会被误命中。

当前 binary `0.5.4` 命中 **2 次**(`SPIKE_VERSION` + 一处别的)。如果某些字符串碰巧含 `0.5.5` 子串,会误判。

### 4.2 修正

```powershell
# 精确匹配 SPIKE_VERSION
$bytes=[System.IO.File]::ReadAllBytes($bin)
$txt=[System.Text.Encoding]::ASCII.GetString($bytes)
([regex]::Matches($txt,'0\.5\.5')).Count
```

或者更简单:U-V20b 直接用 `/health` 端点验证:
```
GET /health  →  { "version": "0.5.5", ... }
```
这比 grep binary **更可靠**(验证的是运行时行为,不是静态字符串)。

**建议**:U-V20b 改为 `/health` 端点验证,grep binary 作为辅助。
