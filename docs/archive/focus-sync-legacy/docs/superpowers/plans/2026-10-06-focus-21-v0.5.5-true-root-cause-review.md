## 3. Claude 诊断的「漏掉的 40%」(真因 #1)

### 3.1 真因:filename_edit_score 把 41477 排在 1001 之前

`sigma-listary-spike/src/uia_inject.rs:706-716`:

```rust
fn filename_edit_score(element: &IUIAutomationElement) -> i32 {
    let automation_id = current_automation_id(element);
    if automation_id == "1148" {
        return 100; // Modern IFileDialog filename combo box
    }
    if automation_id == "1001" {
        return 90;  // Legacy dialog filename Edit
    }
    if automation_id == "41477" {
        return 95;  // Chromium address bar (Edge / Chrome / VS Code / Electron)
    }
    // ...
}
```

**问题**:
- `41477` (Chromium address bar ComboBox) → 95 分
- `1001` (Legacy dialog filename Edit) → 90 分

**41477 赢 1001。**

`F3 baseline`(`uia_inject.rs:649-651`):
```rust
let edit = best_edit.ok_or_else(...)?;
unsafe { value.SetValue(&BSTR::from(target_path)) }?;
```

`best_edit` 由 `filename_edit_score` 选出 → 41477 赢 → F3 baseline `SetValue("C:\\", 41477)` → Chromium ComboBox UIA SetValue → **APPEND 而不是 REPLACE**(Chromium 的 UIA ComboBox ValuePatternSet 实现是 "set text in edit portion",不是 "replace whole string")。

### 3.2 验证:Chromium 41477 出现在 dialog 中

spike.log 显示 `app="#32770"` 但这 **不矛盾**:
- `#32770` = Win32 dialog 窗口类
- Chromium 把 UIA tree 暴露在 `#32770` 窗口内(常见模式:Chrome/Edge Save As dialog 的 Win32 frame 是 `#32770`,内部 UI 是 Chromium 的)
- UIA scan 在 `#32770` 窗口内会发现 `automation_id="41477"` (Chromium address bar) 和 `automation_id="1001"` (Win32 filename Edit) **同时存在**
- `filename_edit_score` 给 41477 95 分 > 1001 90 分 → `best_edit = 41477` → F3 写到 41477 → Chromium ComboBox APPEND

**用户实测看到的现象完全匹配**:
> "第一次会自动在下载弹窗的地址栏,在原有地址后面自动叠加 C:\"

地址栏被污染,**因为 sidecar 把 `C:\\` 写到了 41477 ComboBox (地址栏),而不是 1001 Edit (filename)**。

### 3.3 Claude 的诊断漏了这一点

Claude 在 `2026-10-06-focus-21-v0.5.4-ship-symptom-diagnosis.md §4.2` 提出:

> **假设 H2**:Chromium 41477 element UIA SetValue append
> **可能原因**:Chromium 41477 是 ComboBox 类型,UIA SetValue 调用行为在 Chromium 实现中可能 append 到 .Value 字符串而非 .Edit.Value

Claude 看到了 SetValue append 的症状,但 **没有问为什么 41477 是 best_edit**。

真相是:`filename_edit_score` 给 41477 95 分是 **历史设计错误**。追溯 commit 905db31 时这个函数是为了"WinUI 3 wrapped dialog 的双 score 表",但忘了 `#32770` legacy Chromium dialog 也包含 41477 element。

**评分应该反过来**:
- 41477 (Chromium ComboBox address bar) → **不应该作为 fallback 目标**,因为 Chromium ComboBox SetValue 行为 buggy
- 1001 (Win32 filename Edit) → 是 fallback 的正确目标,Win32 IFileDialog 会把 SetValue("C:\\path") 解释为"导航到 C:\\path"

### 3.4 Claude 的修复方案必须配

Claude 在 `§5.3` 给了 4 个方案:

| Claude 方案 | Mavis 评价 |
|---|---|
| **方案 A**:把 41477 分数从 95 降到 50 | ✅ **正解**(Mavis P0) |
| 方案 B:对 Chromium dialog 显式优先选 1001 | ✅ 等价于方案 A,但更复杂(需要先识别"是 Chromium dialog") |
| 方案 C:对 41477 先 SetValue("") 再 SetValue(target) | ⚠️ 部分解,但 SetValue("") 可能触发 dialog 重置 + flicker |
| 方案 D:走 H1 SendInput 路径(Ctrl+L + type) | ❌ race condition 没解决,SendInput 仍需 dialog 在前台 |

**Mavis 推荐**:Claude 方案 A,但框架要更明确 —— **41477 应该从 best_edit 候选里彻底排除**(return `i32::MIN` 或 `0`),**不是只降低分数**。理由:

1. 即便 41477 = 50,仍然比 0(完全没有命中)高;在某些特殊 dialog 里如果只有 41477,还是会被选中
3. 让 41477 永远不赢 best_edit,彻底关掉"误写到 address bar"的可能

### 4.2 `opened_write_back` 触发链

**触发条件**:`initial_path` (dialog 的初始文件名/路径) ≠ `current` (sidecar 的 current_path)

### 6.3 Sigma FM TDZ 错误证据(用户截图)

  at c (navigator-DJVMws3e.js:2:37962)

- `navigator-XXX.js` + `runtime-core.esm-bundler-XXX.js` = **Vite + Vue 3 打包器**(源码路径:Vue 3 `runtime-core` 包)

## 8. v0.5.5 修复方案(2 文件,~10 行 diff)

### 8.1 Fix A:41477 退出 best_edit 候选(P0,~2 行)

`sigma-listary-spike/src/uia_inject.rs:706-716`:

```rust
fn filename_edit_score(element: &IUIAutomationElement) -> i32 {
    let automation_id = current_automation_id(element);
    if automation_id == "1148" {
        return 100;
    }
    if automation_id == "1001" {
        return 90;
    }
    if automation_id == "41477" {
        // v0.5.5 (2026-10-06 Mavis 复盘): 41477 is the Chromium address bar
        // ComboBox, NOT a filename input. Chromium's UIA ComboBox ValuePattern
        // SetValue behavior is to APPEND (not replace) — using it as fallback
        // target pollutes the address bar instead of navigating the path.
        // Returning MIN ensures 1001 (filename Edit) always wins, and we
        // never accidentally write to the breadcrumb.
        return i32::MIN;
    }
    // ...
}
```

**预期效果**:
- 现代 Edge Save As (`#32770` + Chromium UIA): `best_edit = 1001` (filename Edit) → F3 baseline SetValue → Win32 IFileDialog 解释为"导航到路径" → ✅ 对的
- 旧 Edge Save As (`#32770` + Win32): `best_edit = 1001` → ✅
- WinUI 3 wrapped (Edge Win11): `best_edit = 1001` (因为也有 1001 element) + H1/H2 chain 在外层 → ✅

### 8.2 Fix B:`opened_write_back` sentinel guard(P0,~5 行)

`sigma-listary-spike/src/main.rs:352-371`:

```rust
let current = state.get_current_path();
// v0.5.5 (2026-10-06 Mavis 复盘): opened_write_back was designed for the
// case where extension PUSH is racing with dialog open. If extension is
// broken (TDZ in Sigma FM Vue runtime), state.current_path stays at the
// init sentinel "C:\\" and EVERY dialog gets an unsolicited write of "C:\\"
// to its address bar — pollution that no user path change can fix.
//
// Guard: skip if current equals the init default OR current is empty OR
// dialog path already matches current (defense in depth — initial_path !=
// current already handles this case).
let init_sentinel = cfg.initial_path.as_str();
if !initial_path.is_empty()
    && initial_path != current
    && current != init_sentinel
    && !current.is_empty()
{
    // ... existing write-back logic ...
}
```

**预期效果**:
- extension 正常 PUSH:`current` 是合法路径 ≠ init sentinel → 触发 write-back → ✅ 保持 round-19e 行为
- extension 损坏 (TDZ):`current = "C:\\"` = init sentinel → 不触发 → ✅ 防止 unsolicited pollution
- 还没收到 PUSH 但用户开 dialog:`current` 还是 sentinel → 不触发 → ✅ silent skip(用户可以手动 Sync)
