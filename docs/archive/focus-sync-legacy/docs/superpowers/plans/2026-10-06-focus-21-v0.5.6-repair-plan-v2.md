## 0. v1 计划的根本性错误(Mavis 指出)

### 0.1 T-1(认知错误,🔴 CRITICAL)

v1 计划的 fallback 链路:
```
should_opened_write_back 返回 true
   ↓
main.rs:364  write_path(state, hwnd, current="C:\\", false)
   ↓
writer.rs → inject_folder_path(..., "C:\\", should_commit=false)
   ↓
uia_inject.rs:511  try_set_folder_via_com(hwnd, "C:\\")   ← COM IO 经常失败
   ↓ fail
uia_inject.rs:667  SetValue(1001_edit, "C:\\")              ← SetValue = 填文本
```

**关键问题**:
- `should_commit = false`(Rule 47 强制,不 auto-Invoke)
- `try_set_folder_via_com` 经常失败 → 降级到 SetValue
- SetValue 1001 = 写 filename Edit,不是 address bar
- **不产生任何 dialog 导航**

**这就是用户 100+ 轮最初的原始投诉**:
> "dialog 跳转 but path 字段被污染(breadcrumb updates, but filename field gets overwritten with the path)"
> "dialog 真正跳转 + **不要把路径写进 filename 字段**"

**v1 plan 做的正是被禁止的事。**

### 0.2 v1 plan §4.4 step 2 把"filename box 同步出现"写成 PASS 条件

这是把 bug 当成验收标准。

### 0.3 v1 plan §6 的自相矛盾

v1 §5 结尾:
> "v0.5.6 的 fallback 应该比 v0.5.4 更精准(v0.5.4 写 `C:\`,v0.5.6 写 `state.current_path`,**正常情况下是真实路径**)"

但 "正常情况下" = extension PUSH 正常 = fallback 根本不触发。fallback 只在 PUSH 失败时触发,**那时 `current_path` 必然是 sentinel**。

**逻辑自相矛盾 — 写 null 时决不可信,不能写 null**。

### 0.4 T-2 ~ T-5 简要

| ID | 问题 | 修正 |
|---|---|---|
| **T-2** | `initial_path != current` 语义错位(filename vs directory) | 删掉,恒真无意义 |
| **T-3** | fallback 写 sentinel 自相矛盾 | 删掉 |
| **T-4** | §4.4 step 3 期望 "Sigma FM 导航后 address bar 变 D:\\projects" 但 TDZ 错误让 PUSH 不可能 | 改 |
| **T-5** | Git Bash 语法(`export PATH` / `./spike.exe &`) | 改 PowerShell |

async function syncNow() {
    try {
        const path = await sigma.context.getCurrentPath();
        if (!path) {
            try {
                sigma.ui.showNotification({
                    title: 'Focus Sync',
                    description: 'No current folder (Sigma FM context unavailable).',
                    type: 'warning',
                });
            } catch (e) {}
            return;
        }
        // Check if sidecar received previous push
        let healthR;
        try {
            healthR = await sigma.http.request({ url: `${SIDECAR_HTTP}/health`, method: 'GET' });
        } catch (e) {
            try {
                sigma.ui.showNotification({
                    title: 'Focus Sync',
                    description: 'Sidecar not reachable. Open Task Scheduler → KizemoFocusSync → Run.',
                    type: 'error',
                });
            } catch (e) {}
            return;
        }
        const health = JSON.parse(healthR.body || '{}');
        await pushNow(path);
        try {
            const desc = health.first_push_received === false
                ? `首次 PUSH 已发送: ${path}\n(后续 navigation 将自动同步)`
                : `Synced: ${path}`;
            sigma.ui.showNotification({
                title: 'Focus Sync',
                description: desc,
                type: 'success',
            });
        } catch (e) {}
    } catch (e) {}
}

## 3. v2 计划决策 C 起点 — v0.6 治本方向(强烈推荐并行启动)

### 3.1 根因

100+ 轮反复:**依赖一个已知失效的外部 API**(`sigma.context.onPathChange`)。即使 v0.5.6 恢复 fallback,只要 Sigma FM TDZ 错误还在,用户永远拿不到真实路径同步。

### 3.2 v0.6 方案候选(对比)

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **C-1 窗口标题轮询** | sidecar 每 500ms 检查 Sigma FM 主窗口标题(目录通常在标题) | 不依赖 extension | Edge case 多(标题格式不固定) |
| **C-2 配置文件读取** | sidecar 读 Sigma FM 的 last-opened-folder 配置 | 简单可靠 | 需要知道配置路径 |
| **C-3 Shell notification** | sidecar 注册 Windows shell change notification | 实时 | 仅适用于部分场景 |
| **C-4 修 Sigma FM TDZ** | 改 Sigma FM 主项目 navigator 模块 | 治本 | 在主项目仓库,本仓库无权限 |

## 5. 元规则沉淀

### 5.1 Rule 58(NEW,来自 T-1)

```markdown
### 规则 58 — SetValue(1001) ≠ 导航

**触发**:v0.5.6 计划 v1 把 `SetValue(1001)` 当成"导航",实际只是填文本。

**规则**:
1. UIA `ValuePattern::SetValue` 到 `1001` (filename Edit) = 把字符串塞进 filename 框,**不改变 dialog 当前目录**
3. 只有 `IFileDialog::SetFolder` (COM) 才能真正导航 dialog
4. `should_commit=false` (Rule 47) 禁止 auto-Invoke Save
5. 因此"SetValue 1001 + should_commit=false" = **写 filename 污染**,不是 sync
7. **不要把"filename 同步出现"当成 sync 成功的验收标准**
```

### 5.2 Rule 59(NEW,来自 T-3 + T-4)

```markdown
### 规则 59 — 验收标准必须 100% 可通过

**触发**:v0.5.6 计划 v1 §4.4 step 3 期望"Sigma FM 导航后 address bar 变 D:\\projects",但 §6.1 承认 extension 不 PUSH,这条不可能通过。

**规则**:
1. 每个验收标准必须能在测试环境中 100% 通过
2. 如果验收标准依赖已知失败的上游,这是计划问题不是测试问题
4. 验收标准不能写"或"'或"'、 "可能" "可能"'等真值不明的条件
6. 在写验收标准前先问:"在没有 path Sigma FM 那部分时,这条能 PASS 吗?"
```

### 5.3 Rule 60(NEW,综合)

```markdown
### 规则 60 — fallback 设计必须诚实面对 trade-off

**触发**:v0.5.6 计划 v1 §6 自相矛盾(v0.5.4 写 C:\\, v0.5.6 写 state.current_path 正常情况下是真实路径)。

**规则**:
1. fallback 必须明确"降级到什么",不能模糊地说"降级模式"
3. 若 commitment 涉及污染 (filename 不可), 必须在 plan 里明确告知用户
5. 用户接受 trade-off 后再 ship,不能船到江心才告诉用户"这是 bug 不是 feature"
7. 强烈推荐 fallback 路径 = "什么都不做 + 明确错误信息",而不是"换个方式重现原 bug"
```
