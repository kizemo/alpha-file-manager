## 1. 完整复盘链

### 1.1 v0.5.5 退步根因(Mavis Round 21/22)

12 个 Fix 已应用,但 v0.5.5 binary 退步:

- **Fix F** `default_value = ""`(从 `C:\\` 改)
- **Fix B** `first_push_received` gate
- **Fix B3** `should_opened_write_back` 三条件 helper
- **Fix D** skip sentinel log
- **Fix N-4** early-return mark in dedup branch

**Fix B + Fix F 共谋**:`current = ""` + `first_push_received=false` → `should_opened_write_back` 永远 false → opened_write_back 永远 skip → 用户零 sync。

**对比 v0.5.4 baseline**:`current = "C:\\"` + `if !target.is_empty()` 兜底 → 手动部署时代 sync 一直能 work。

### 1.2 v1/v2/v3 plan 演进(Claude)

| 版本 | 关键思路 | 问题 |
|---|---|---|
| v1 | fallback SetValue("C:\\", 1001_edit) | Mavis Round 28: 这正是 100+ 轮最初要修的 bug(写 filename 框,不导航)|
| v2 | 决策拆分 A/B/C(恢复 fallback vs 只诊断 vs v0.6 治本)| 仍归因"Sigma FM 环境坏 → sync 不可达" |
| **v3** | **manual deploy 是黄金基线**(Rule 61)+ 修复 gate + 不动 installer(Rule 62)| 漏了 MiniMax 发现的缺陷 A/B/C |

### 1.3 Phase 4 sandbox 修复(MiniMax,已实施)

MiniMax 没改 sidecar 一行,只做:

- **Hook 1** 构建期 sandbox 验证(`sigma-file-manager/scripts/build-with-sidecar.ps1`)
- **Hook 2** 部署期验证(`release/extension-installer/manual-install.ps1`,拷贝前)
- **Hook 2b** 注册期验证(`release/extension-installer/register.ps1`,已部署副本)
- **Hook 3** 提交期验证(`.git/hooks/pre-commit`)
- **Hook 4** 体检脚本(`scripts/scan-sandbox-dynamic.cjs`)

**WHY**: `validateExtensionCode()` 拒绝任何 sandbox regex 匹配(注释也算)→ loader.ts throw BEFORE `new Worker()` → extension 静默不加载,sidecar 收 0 请求。

**双向测试**: Hook 1/3 用 fixture 验证 gate 确实拦截违规。

### 1.4 MiniMax 缺陷 A/B/C 实证(不动 sidecar,严格 Iron Law)

| 缺陷 | 实证 | 候选修复 |
|---|---|---|
| **A 死 HWND 写入** | hwnd=1707512 `IsWindow=False`,被写入 → `unsupported_dialog_type` 误报 + 污染 counter | P0-1: IsWindow 检查 + 新错误码 `dialog_gone` |

### 2.2 改动 1:`state.rs:131` — gate 简化

**当前 v0.5.5(bad)**:
```rust
pub fn should_opened_write_back(&self, initial_path: &str, current_path: &str) -> bool {
    !initial_path.is_empty()
        && initial_path != current_path
        && self.has_first_push_received()
}
```

**新 v0.5.6(good)**:
```rust
pub fn should_opened_write_back(&self, initial_path: &str) -> bool {
    !initial_path.is_empty()
}
```

**WHY**:
- `initial_path != current_path` 是 filename vs directory 语义错位(Mavis Round 28 T-2)
- `first_push_received` gate 关闭了唯一兜底路径(v3 plan Rule 55)
- v0.5.4 baseline 时代的检查就是 `!is_empty()`,这是 manual deploy 黄金基线

**真正的去重** 由 `main.rs:401-408` `last_known_path` 负责(已实现)。

### 2.3 改动 2:`main.rs:30` — sentinel 退回


**新 v0.5.6(good)**:

**WHY**: Fix F + Fix B 共谋,两者必须一起退回(v3 plan)。

### 2.4 改动 3:删 skip sentinel 分支

### 2.5 改动 4:`writer.rs::write_path` 入口 — IsWindow 检查 + 新错误码

**新增代码**:
```rust
use windows::Win32::UI::WindowsAndMessaging::IsWindow;

pub fn write_path(state: &crate::state::AppState, hwnd_isize: isize, target: &str, auto_confirm: bool) -> WriteOutcome {
    if hwnd_isize == 0 {
        return WriteOutcome::Failed("hwnd is 0".into());
    }
    let hwnd_u32 = hwnd_isize as u32;
    
    // v0.5.6 P0-1: 死 HWND 检查(MiniMax 实测缺陷 A)
    if !unsafe { IsWindow(HWND(hwnd_isize as *mut core::ffi::c_void)) }.as_bool() {
        // 顺手清掉注册表噪声,避免 focus-19 阈值污染
        state.remove_dialog(hwnd_u32);
        // 关键:不复用 unsupported_dialog_type,否则继续污染 focus-19 告警
        return WriteOutcome::Failed("dialog_gone".into());
    }
    
    // ... 现有逻辑
}
```

**WHY**:
- 死 HWND 写入产生假的 `unsupported_dialog_type`(Mavis 缺陷 A)
- 必须用**新错误码** `dialog_gone`,否则又把"对话框已关"和"WinUI 3 不支持"混在一起
- **`dialog_gone` 不得累加 `unsupported_dialog_count`**(`writer.rs` 中只有 `unsupported_dialog_type` 累加,新错误码天然不累加)

### 2.6 改动 5:`http_server.rs::respond_json` — charset utf-8

**修改**:
```rust
// 之前
Response::from_string(body).with_header(... "Content-Type: application/json" ...)

// 新
Response::from_string(body).with_header(... "Content-Type: application/json; charset=utf-8" ...)
```

**WHY**: `Content-Type` 不带 `charset` 时,中文 Windows 上 PowerShell 5.1 默认 GBK 解码 → UTF-8 中文路径乱码(MiniMax §1.5 真实产品 bug)。

## 5. 沉淀规则(Memory + MEMORY.md 索引)

### Rule 55 — opened_write_back 必须保留 fallback 路径

任何 gate/守卫实施前必须回答:"如果这个 gate 永远不通过,系统还剩什么可用路径?"如果答案是"什么都不剩",这个 gate 是**功能删除**,不是优化。

### Rule 56 — "改动生效" U-V ≠ "功能可用" U-V

每 ship 必须有端到端功能 U-V(用户可见行为改变),不能全部由 grep / binary probe / unit test 组成。若无法做端到端验证,必须明说。

### Rule 57 — 单点审查通过 ≠ 系统行为正确

每个 Fix 单独 review 通过 ≠ 多 Fix 组合行为正确。任何 plan 引入 ≥ 2 个 Fix 时,必须审查 Fix 之间的交互效应(B + F 共谋)。

### Rule 58 — SetValue(1001) ≠ 导航

`ValuePattern::SetValue` 到 1001 (filename Edit) = 把字符串塞进 filename 框,**不改变 dialog 当前目录**。只有 `IFileDialog::SetFolder` (COM) 才能真正导航 dialog。**不要把"filename 同步出现"当成 sync 成功的验收标准**。

### Rule 59 — 验收标准必须 100% 可通过

每个验收标准必须能在测试环境中 100% 通过。验收标准不能依赖已知失败的上游。

### Rule 60 — fallback 设计必须诚实面对 trade-off

fallback 必须明确"降级到什么",若涉及污染 (filename 不可), 必须在 plan 里明确告知用户。

### Rule 61 — 手动部署是黄金基线,installer 失败 ≠ sync 不可达

当某 deploy path 之前能 sync,退步 = binary/installer bug,**不是 sync 目标不可达**。"环境归因"是逃避。

### Rule 62 — 修复 v0.5.x binary 时不动 installer

v0.5.6 fix 范围 = sigma-listary-spike/ Rust 代码 + release/extension/{dist,package.json}。installer 调试是 v0.5.7+ 问题(独立 P1)。

### Rule 63 — 不要把诊断严格度当成 ship 阻塞(NEW)

MiniMax Iron Law 严格执行 → 缺陷 C 诊断完美 → 但 v0.5.6 ship 被阻塞。规则:**现象已确认 + 候选修复路径明确 + 不阻塞核心修复**时,可以 ship,v0.5.7+ 继续治本。**严格不等于僵化**。

### Rule 64 — 测量工具不能验证自己的结论(NEW,from MiniMax §1.5)

判定乱码/编码/性能之前,必须先证明读取工具没有引入问题。两种独立方式解码同一份数据,结果一致才下结论。

### Rule 65 — Content-Type 不带 charset 是真实产品 bug(NEW)

任何 HTTP JSON 响应必须 `Content-Type: application/json; charset=utf-8`。否则中文 Windows 客户端默认 GBK 必乱码。

## 7. 元判断 / 教训

### 7.1 100+ 轮原地踏步的最终归因

不是单一原因,是**多个相互叠加的失败模式**:

| 模式 | 体现 |
|---|---|
| **测量工具错** | MiniMax §1.5: 用 GBK 默认解码 UTF-8 数据 → 假根因 |
| **gate 加错位置** | Fix B + Fix F 共谋关闭唯一兜底路径 |
| **审查盲区** | 5 轮 review 没看"功能是否还在"(Rule 56) |
| **归因错误** | 把 sync 不可达推给环境(Rule 61 反驳) |
| **盲改僵化** | Iron Law 严格执行变成 ship 阻塞(Rule 63) |
| **漏独立 bug** | Phase 4 sandbox 完全是独立 bug 类别,100+ 轮没看到 |

### 7.2 100+ 轮不可能靠"再做一轮 review"解决

**根本问题**: 没有 functional U-V + 没有跨层审查 + 没有测量纪律。三者同时缺,任何 review 都会重新发现旧 bug 或新 bug,但**无法收敛**。

### 7.3 v0.5.6 是真正 ship-ready 的关键

需要同时:
1. **修复 gate bug**(v3 plan 核心)
