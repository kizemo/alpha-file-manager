## 1. U-1(CRITICAL):验收标准与改动能力不匹配

### 1.1 完整写入链路推演

```
main.rs:352   let current = state.get_current_path();          // "C:\\"
main.rs:355   if state.should_opened_write_back(&initial_path)  // !is_empty() → true
main.rs:364   write_path(&state, hwnd, &current, false)         ← should_commit = false
writer.rs:73  inject_folder_path(state, hwnd, "C:\\", false)
uia_inject.rs:511  try_set_folder_via_com(hwnd, "C:\\")
                 └─ AccessibleObjectFromWindow(OBJID_NATIVEOM)
                    Chromium 实现的 IAccessible 通常不支持 IServiceProvider/IFileDialog
                    → QueryService 失败 → return false
uia_inject.rs:518  inject_via_uia(hwnd, "C:\\", false)
uia_inject.rs:610  is_winui3_wrapped = has_filename_host && has_1001
                   #32770 legacy dialog → false → 跳过 H1/H2
uia_inject.rs:667  value.SetValue(&BSTR::from("C:\\"))            ← 只改 filename 文本
uia_inject.rs:662  // should_commit is ignored at the injection layer
```

### 1.2 源码原文佐证

`uia_inject.rs:662-666`:
```rust
// v0.5.1: should_commit is ignored at the injection layer — the user
// wants manual save confirmation for every code path. (the auto-Invoke Save
// was removed at the user's request.)
```

**全链路没有任何一处 Invoke / Enter / SendMessage。**

### 1.3 三个关键推论

**推论 1:`SetValue` 到 1001 只改文本,不导航**

legacy `#32770` IFileDialog 的 filename Edit 接受完整路径,但**只有在 commit(点保存 / 按 Enter)时才会解析并跳转**。不 commit = 文本停留在框里,目录不变。

**推论 2:`is_winui3_wrapped == false` 时 H1/H2 完全不跑**

`uia_inject.rs:610-647` 的 4-layer chain 只在 `is_winui3_wrapped` 为 true 时进入。用户的 dialog 是 `#32770`,从 spike.log 的 `strategy:"uia"`(F3 出口)可以确认走的是 F3 兜底。

**推论 3:COM SetFolder 是唯一可能真正导航的路径,但没有证据它成功过**

`writer.rs:77` 把 `ComSetFolder` 和 `AddressBarWritten` **都映射成 `WriteOutcome::UiaSetValue`**,两者在 spike.log 里都是 `strategy:"uia"` —— **无法区分**。

而且 `tracing::warn!` / `info!` 不写 spike.log(实测:spike.log 里 `COM SetFolder unavailable` / `IFileDialog::SetFolder succeeded` 命中数均为 **0**)。

### 1.4 结论

**v3 §5.3 item 5「dialog 当前目录真的变化」在 v3 的改动下 100% 无法通过。**

这不是"可能失败",是"必然失败"。如果照此 ship gate 执行,会卡在第 5 条,且查不出原因 —— 这正是过去 100+ 轮的困局。

## 4. U-4(HIGH):「手动部署能 sync」缺乏证据

### 4.1 spike.log 全量统计

```
SpikeError          414
DialogDetected       71
Write                70      ← 全部 strategy:"uia"
Read                 61
WriteFailed          24
ForegroundChanged    23
```

**71 个 dialog 检测,70 个 Write,全部 `strategy:"uia"`。**

`strategy:"uia"` 来自 `writer.rs:78` 的 `DialogOutcome::AddressBarWritten`,即 `inject_via_uia` 返回 `Ok(())` —— 也就是 **F3 SetValue 到 filename 成功**。

### 4.2 用户说的「之前有可能同步到地址栏、文件名处」

这句话与实测**完全一致**:用户看到的现象就是「路径字符串出现在地址栏或 filename 字段」。

**但那不是导航。** 那是 SetValue 写文本 —— 也就是用户第一条消息里明确要修的:

> 不要把路径写进 filename 字段

### 4.3 所以 v3 的 Rule 61 建立在一个误解上

Rule 61 说「手动部署能 sync,所以 sync 目标可达」。

**但「同步」的定义被偷换了**:
- 用户心里的 sync = dialog 跳转到目标目录
- 实测的 sync = 路径字符串出现在某个输入框里

**如果把目标定义为「路径出现在输入框」,那 v0.5.6 的 5 行改动确实能恢复。**
**如果定义为「dialog 真正跳转」,那 v3 改动完全无效。**

**这个定义必须先澄清,否则再改 10 轮也还是原地踏步。**

### 4.4 Rule 61 / 62 的问题

| 项 | 问题 |
|---|---|
| 前提 | 「手动部署能 sync」未区分「导航」与「写文本」 |
| 归因 | 「installer 失败」与实测矛盾(U-2) |
| 编号 | Rule 61 编号 1,3,5,7(缺 2,4,6);Rule 62 编号 1,2,4,6 |
| 规则 2 | 措辞混乱「v0.5.5 installer fail ≠ sync goal impossible」重复两次(1 和 5) |

**建议**:Rule 61 重写为「目标定义必须先澄清」,而不是「installer 失败 ≠ sync 不可达」。

### 6.4 改动 3(新增,**若目标是 B 则必须**):让 COM SetFolder 的结果可见

**这是本优化方案最重要的补充。**

当前 `try_set_folder_via_com` 的所有成败信息都在 `tracing::warn!/info!` 里,**不进 spike.log**,导致:
- 我们永远不知道它是成功导航了,还是失败了才降级到 F3
- v3 §5.3 item 5 无法判定

```rust
// uia_inject.rs — try_set_folder_via_com 的每个 return false 前加 spike.log
// 需要从 crate::events::Event + crate::logger::log_event 引入

fn try_set_folder_via_com(dialog_hwnd: u32, target_path: &str) -> bool {
    // AccessibleObjectFromWindow 失败
    if ...is_err() || ppv.is_null() {
        log_event(&Event::SpikeError {
            kind: "com_setfolder_fail".into(),
            message: format!(
                "AccessibleObjectFromWindow(OBJID_NATIVEOM) failed \
                 hwnd={dialog_hwnd} target='{target_path}' \
                 (Chromium-hosted #32770 不支持 IFileDialog NativeOM)"
            ),
            ts: now_iso8601(),
        });
        return false;
    }

    // QueryService(SID_STopLevelBrowser) 失败
    let file_dialog: IFileDialog = match sp.QueryService(&SID_STopLevelBrowser) {
        Ok(f) => f,
        Err(e) => {
            log_event(&Event::SpikeError {
                kind: "com_setfolder_fail".into(),
                message: format!(
                    "QueryService(SID_STopLevelBrowser) failed: {e:?} \
                     hwnd={dialog_hwnd} target='{target_path}'"
                ),
                ts: now_iso8601(),
            });
            return false;
        }
    };

    // ... 其余分支同理 ...

    // 成功时
    log_event(&Event::SpikeError {
        kind: "com_setfolder_ok".into(),
        message: format!(
            "IFileDialog::SetFolder succeeded hwnd={dialog_hwnd} target='{target_path}' \
             → 真正导航"
        ),
        ts: now_iso8601(),
    });
    true
}
```

**同时修 `writer.rs` 的可观测性缺陷** —— 让 COM 成功与 UIA 成功在日志里可区分:

```rust
// writer.rs:76-89
match dialog_outcome {
    DialogOutcome::ComSetFolder => {
        log_event(&Event::Write {
            hwnd: hwnd_u32,
            app: String::new(),
            target: target.to_string(),
            strategy: "com_setfolder".into(),   // ← 改:原来是 "uia"
            ts: now_iso8601(),
        });
        WriteOutcome::UiaSetValue
    }
    DialogOutcome::AddressBarWritten => {
        log_event(&Event::Write {
            hwnd: hwnd_u32,
            app: String::new(),
            target: target.to_string(),
            strategy: "uia_setvalue".into(),    // ← 改:更精确
            ts: now_iso8601(),
        });
        WriteOutcome::UiaSetValue
    }
    // ...
}
```

> ⚠️ 注意:`writer.rs` 的 `Write` 结构没有 `app` 字段传入(当前 `write_path` 签名里没有 app),实施时需确认 `Event::Write` 的字段定义,可能需要传空串或改签名。

### 6.5 改动 4(若目标是 B):WinUI 3 wrapped 的 H2 路径可能才是真正导航

`uia_inject.rs:610` 的 `is_winui3_wrapped` 门槛导致用户的 `#32770` dialog 完全跳过 H1/H2。

而 Claude 在 Rule 55 里记录过用户反馈:

> 「瀑布图先显示,再消失」—— H2 fallback 的 SetValue target → 50ms sleep → SetValue original 副作用(address bar 闪一下恢复)

**这说明 H2 在某些 dialog 上确实让 breadcrumb 变化过。** H2 的机制是:

```rust
value.SetValue(target_path);      // WinUI 3 的 1001 是 dual-role → 触发导航
sleep(50ms);
value.SetValue(original);         // 恢复文件名,breadcrumb 保留
```

**如果 breadcrumb 真的变了,那就是真导航。**

**建议**:v0.5.6 先不改 `is_winui3_wrapped` 门槛(风险高),而是在 §6.4 的日志里确认用户的 dialog 到底走了哪条路径,再决定。

| Rule 61 / 62 | ❌ 前提错误 + 编号断裂(U-4/U-5) |

### 8.3 缺失的

**最关键的缺失:整个计划没有任何一处讨论「SetValue 不等于导航」。**

v3 花了大量篇幅论证「恢复兜底路径」,但没问「兜底路径恢复后,到底发生了什么」。

**这是 v0.5.5 → v0.5.6 → v0.5.7 反复绕圈的根源:每次都在讨论「要不要写」,没人问「写了之后会发生什么」。**

## 9. 沉淀规则(替代 Rule 61 / 62)

### Rule 63 — 写操作前必须回答「这个写操作会产生什么用户可见效果」

```markdown
### 规则 63 — 区分「写入」与「生效」

**触发**:v0.5.6 计划审核(Round 30)

**事实**:sidecar 的 F3 路径是 `SetValue(best_edit=1001, path)`,
而 `should_commit` 恒为 false(v0.5.1 起 Rule 47)。
→ SetValue 只改 filename 文本,**不触发导航**。
→ spike.log 的 `Write strategy="uia"` 只证明「写入成功」,
   不证明「dialog 跳转了」。

**规则**:
1. 每个写操作必须能回答:「用户可见的效果是什么?」
   - SetValue 到 filename → filename 字段变化(**不是导航**)
   - COM IFileDialog::SetFolder → 当前目录变化(**真导航**)
   - Invoke(Save)/SendMessage(Enter) → dialog 关闭(**commit**)
2. `writer.rs` 把 `ComSetFolder` 与 `AddressBarWritten` 都映射成
   `WriteOutcome::UiaSetValue`,导致日志无法区分两者。
   → 必须修,否则无法判断导航是否发生。
3. 验收标准必须区分「日志有 Write」与「用户看到目录跳转」。
   只有前者通过不算功能可用。
```

### Rule 64 — 「定义」必须先于「修复」

```markdown
### 规则 64 — 动手前先确认目标的可观测定义

**触发**:v0.5.6 v3 审核(Round 30)

**问题**:「同步」有两个截然不同的定义:
  A. 路径字符串出现在输入框(历史行为,v0.5.4 能做到)
  B. dialog 当前目录真正跳转(用户第一条消息明确要的)

按 A 判定 → v0.5.6 的 5 行改动足够
按 B 判定 → 5 行改动完全不够,需要攻 COM SetFolder / WinUI 3 H2 路径

**规则**:
1. 修复计划的第一节必须是「目标的可观测定义」,不是「根因分析」。
2. 若目标有多个可能定义,先与用户确认,再写计划。
3. 验收标准必须能区分不同定义,否则 ship gate 会给出虚假 PASS。
```
