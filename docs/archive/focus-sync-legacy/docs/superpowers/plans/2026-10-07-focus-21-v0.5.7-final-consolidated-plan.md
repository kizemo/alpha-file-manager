## 2. 本轮新发现(我核实了 Claude 的源码细节,发现我错了)

Claude §3.2 指出:

> `main.rs:355` 的 `initial_path` 是 `reader::read_path(hwnd)` 返回的 **dialog 真实文件名**,
> 不是目录路径。

**我逐行核实了 `main.rs:288-408`,Claude 是对的。我上一轮基于「`initial_path != current` 是去重」
的论证是错的。**

### 2.1 更正:改动 1 应当拆分,而不是整体拒绝

我上一轮说「删掉 `initial_path != current` 会重新引入 round-17 闪写回归」。**这个论证不成立**:

```rust
// main.rs:306
let initial_path: String = spike::reader::read_path(info.hwnd)?;   // 返回 filename 文本
// main.rs:352
let current = state.get_current_path();                            // Sigma FM 推送的目录
// main.rs:355
if state.should_opened_write_back(&initial_path, &current)
//  state.rs:131
!initial_path.is_empty() && initial_path != current && self.has_first_push_received()
```

`initial_path` 是对话框里的**文件名**(实测样本:`11.politics`、`dmp_全店单品_2025-06-06.xlsx`、
`图库`、`Adobe`),`current` 是**目录**(`E:\resource`)。
拿文件名比目录,**恒为真** ⇒ 这个条件**从来就没有在做去重**,它是一条死条件。

日志实测佐证(64 条 `opened_write_back`):

```
dialog='dmp_全店单品_2025-06-06.xlsx'   current='C:\'
dialog='图库'                            current='E:\resource'
dialog='11.politics'                     current='E:\resource'
```

**所以把改动 1 拆成两半:**

| 编号 | 内容 | 判定 |
|---|---|---|
| **C-1a** | 删掉 `initial_path != current` | ✅ **应做** —— 它是恒真的死条件,还带 filename/directory **类型语义错误** |
| **C-1b** | 删掉 `has_first_push_received()` | ❌ **必须保留** —— 见 §1.2,删了会把空串写进对话框 |

### 2.2 新发现:`last_known_path` 是死字段,注释描述的去重从未实现

`main.rs:401-402` 的注释写着:

> *Update last_known_path so subsequent Opened events for the same hwnd
> see paths match and skip the write.*

但全仓库检索 `last_known_path`:

```
events.rs:20    字段定义(DialogClosed 负载)
state.rs:23     字段定义(DialogInfo)
main.rs:332     赋值 initial_path
main.rs:406     赋值 current
```

**写了 4 处,从来没有被读来做任何比较。** 注释描述的去重机制**在代码里不存在**。

这是一个**诚实性缺陷**:注释承诺了一个不存在的保护,
后来者(包括 Claude 和我)据此推断「有去重保护」,从而得出错误结论。

### 2.3 ⚠️ 但我**不**把它算作当前活跃的 bug —— 克制结论

`last_known_path` 缺失 + `initial_path != current` 无效 ⇒ Opened 回写路径**确实没有有效去重**。
按理说同一次会话的重复 Opened 事件会造成闪写循环(round 17 回归)。

**但历史数据不支持「当前正在闪写」这个结论。** 重复样本的时间间隔:

```
12:18:09 → 12:18:20     (11 秒)
14:41:12 → 14:42:07     (55 秒)
14:42:07 → 14:48:51     (6 分 44 秒)
10-07 14:02:46 → 14:20:22  (17 分 36 秒)
```

这些间隔**远大于** 8ms 的轮询周期,是**多次独立的对话框会话**(同一文件被反复打开),
不是单次会话内的闪写。

**判定:潜在风险(代码诚实性缺陷),当前无证据表明造成实际危害。**
优先级 **P2**,随 C-1a 一并修复,不单独占用一次改动。

> 这一条也是给我自己的提醒:**发现了机制缺失 ≠ 证明了危害发生。**
> 两次都得有证据。

| **A-1** | `write_path` 入口 `IsWindow` + 独立错误码 `dialog_gone` + `remove_dialog` | `writer.rs` | P0 | 低 |

**C-1a 的具体形态**(把死字段救活,顺带修掉类型语义错误):

```rust
// state.rs —— 让 last_known_path 从死字段变成真正生效的去重依据
pub fn should_opened_write_back(&self, dialog_path: &str, current_path: &str) -> bool {
    !dialog_path.is_empty()                     // 读不到对话框就别写
        && self.has_first_push_received()       // ★ 保留(Fix B)
        && self.dialog_needs_write(current_path) // ★ 新增:真正读 last_known_path
}

fn dialog_needs_write(&self, current_path: &str) -> bool {
    match self.get_dialog(self.last_opened_hwnd) { ... }   // 或按 hwnd 查注册表
        Some(d) => d.last_known_path != current_path,
        None    => true,
    }
}
```

**要点**:签名里把参数名从 `initial_path` 改成 `dialog_path`,
避免再次与 `main.rs:30` 的 CLI 同名变量混淆 —— 这正是 Claude §3.2 承认的那个坑。

## 6. 规则沉淀

### Rule 66 — 定性「异常 / 永久 / 结构性」前,先看全量分布
最近 N 行只说明最近,**分布**才说明性质。
*(Claude 已采纳,原文保留)*

### Rule 67 — 看代码不够,看「触发路径 × 实测结果」的相关性
*(Claude 已采纳,原文保留)*

### Rule 68(新增)— 读代码时 trace 变量定义,不从签名/命名推断语义 ★
`initial_path` 同时是 CLI sentinel(`main.rs:30`)和对话框文件名(`main.rs:306`),
两个同名不同作用域的变量,让 Claude 和我都误判了「Fix B + Fix F 共谋」。

**规则**:看到一个变量参与逻辑判断时,必须追到它的**绑定点**,
确认它装的是什么语义(路径?文件名?句柄?),而不是从参数名推断。

### Rule 69(新增)— 「注释承诺的保护」不等于「保护存在」 ★
`main.rs:401` 的注释详细描述了一个基于 `last_known_path` 的去重机制,
但该字段**从未被读**。后来者据此推断「有去重保护」,直接导致了错误的回归风险评估。

**规则**:
1. 看到注释声称存在某个保护,**必须 grep 验证该状态真的被读**
2. 只写不读的字段 = 死状态,要在评审中显式标记
3. 注释与代码不一致时,**以代码为准**,并把不一致本身当作缺陷上报

### Rule 70(新增)— 「机制缺失」与「危害已发生」需要两份证据 ★
本轮发现去重机制完全缺失,但时间戳分析显示重复写入间隔在**秒级以上**,
属于多次独立会话,**不构成**闪写循环的证据。

**规则**:发现了机制层面的问题,不等于证明了它正在造成危害。
两者需要**分别取证**,否则就是夸大声势、消耗团队信任。
严重性判定:机制缺陷但无危害证据 → P2;机制缺陷且有危害证据 → P0。

### Rule 71(新增)— 互补机制不可单独回退
Fix B(`first_push_received` gate)与 Fix F(`default_value=""`)是同一个保护机制的两半:
gate 挡住的正是 Fix F 引入的空串。单独回退任一半,后果都会**比回退前更糟**
(写 `C:\` 或写空串)。

**规则**:当两个改动被注释/文档描述为「针对同一个现象」时,
**必须当作原子单元一起评估和取舍**,不能因为「其中一个看起来有问题」就单独回退。
*(这条正是 Claude §2.2「两者不是共谋」的修正版 —— 它们确实相关,只是相关方向相反:
Fix B 正确,Fix F 也没有独立缺陷。)*
