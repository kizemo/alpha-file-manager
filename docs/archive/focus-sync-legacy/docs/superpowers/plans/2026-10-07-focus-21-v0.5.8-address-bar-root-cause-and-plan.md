## 2. 为什么"填不进去":`SetForegroundWindow` 已经存在,但不够

### 2.1 关键更正 —— 我上一版方案说错了

我上一版把 **B-1「提前台对话框再试 H1」列为"新增工作"**。**这是错的。**

`uia_inject.rs:262-263` 里**早就有了**:

```rust
let _ = AllowSetForegroundWindow(ASFW_ANY);
let _ = SetForegroundWindow(hwnd);

let current_fg = GetForegroundWindow();
if current_fg != hwnd {
    warn!("... is not foreground (current={current_fg:?}); aborting to trigger H2 fallback.");
    return false;        // ← H1 在这里放弃
}
```

代码注释自己都写了:*"May fail under the Vista+ foreground lock; we proceed regardless."*

**所以 B-1 不是"新增功能",而是"补全 Windows 标准做法"。**

### 2.2 缺的是两样

Windows 从 Vista 起有前台锁:一个**非前台、非用户发起**的进程不能随意抢前台。
标准解法是 **`AttachThreadInput` + `SetForegroundWindow` + `BringWindowToTop`**,而当前代码只用了裸的 `SetForegroundWindow`。

而且 `GetForegroundWindow()` 是**紧接其后立即调用**的 —— `SetForegroundWindow` 是**异步**的,
没有条件等待就是拿旧值。这解释了日志里的 `current=HWND(0x0)`。

### 2.3 实证:`SetForegroundWindow` 在哪种情况下有效

| 触发路径 | 对话框是否已在前台 | `SetForegroundWindow` | H1 结果 |
|---|---|---|---|
| `opened_write_back`(对话框刚打开) | **是** | 不需要成功 | ✅ 48/48 成功 |
| `/set_path`(用户在 Sigma FM 操作) | **否**(前台是 Sigma FM) | 被前台锁拒绝 | ❌ 48/48 失败 |

**这不是"偶发失败",是前台锁的确定性表现。**

## 3. ★ U-1 已回答:地址栏**确实**出现了路径 —— 真正的修复是「按 Enter」

> **用户实测:打开下载弹窗后,地址栏里出现过路径文本。**

### 3.1 这个答案改变了整个诊断

| 原假设 | 状态 |
|---|---|
| H1 填不进地址栏(前台锁) | ❌ 对 `opened` 路径不成立 —— 用户看得见路径 |
| 需要 `AttachThreadInput` 才能填进去 | ⚠️ 降级为次要(仅 `/set_path` 路径可能仍需要) |
| **真正的缺口** | ✅ **代码填完之后故意不按 Enter** |

```rust
// uia_inject.rs:319-321
info!("... path dispatched ({total} events, **no Enter**)");
// uia_inject.rs:247
/// 7. **NO Enter** (Rule 47 — user wants manual Save confirmation).
```

### 3.2 因此用户的完整体验链是

```
对话框打开 → H1 填入地址栏(用户看得见,日志也证实)
          → 【没有 Enter】→ 对话框不跳转,文件列表不动
          → 用户说「目录不能同步」
```

**H1 从来没有失败过。它只是停在最后一步。**

### 3.3 关键澄清:导航 ≠ 保存(Rule 47 被误读了)

Rule 47 的原文是「不要自动 **Save**」。但在地址栏按 Enter 只做**导航**
(文件列表跳到目标目录),**不会点击保存按钮,不会提交任何文件**。

| 动作 | 语义 | 用户是否想自动 |
|---|---|---|
| 地址栏填路径 + Enter | **导航**到该目录 | ✅ 想 —— 这就是「同步」的定义 |
| 点击「保存」按钮 | **提交**文件 | ❌ 不想 —— Rule 47 的本意 |

**所以「填入地址栏后按 Enter」不违反 Rule 47,它是 Rule 47 想要的效果。**
这是本轮最重要的认知修正 —— 我们一直以为 H1「故意不完成」,其实它「完成了一半」。

### 3.4 ⚠️ 但按 Enter 有风险,必须加护栏

**如果焦点其实在文件名框(1001)上,Enter 会触发保存。**
所以 Enter 之前必须确认焦点在地址栏。

代码里已有现成的护栏素材 —— I1 焦点校验(`uia_inject.rs:323-341`):

```rust
let focused_hwnd = GetFocus();
let aid = current_automation_id(&elem);
if aid == "1001" || name.to_lowercase().contains("file name") {
    warn!("focused on filename box (1001) — SendInput may pollute filename");
}
```

**修正版 H1 序列:**

```
1. Ctrl+L                     ← 聚焦地址栏(已有)
2. Home + Shift+End           ← 全选(已有)
3. 输入路径                    ← 逐字符(已有)
4. ★ 校验焦点:aid != "1001"   ← 已有素材,改为阻断式
5. ★ 按 Enter(条件执行)       ← 新增
6. post-SendInput 焦点复核     ← 已有(改为 INFO 级日志)
```

**第 4 步是硬护栏**:焦点落在 1001 时**绝对不按 Enter**,直接降级到 H2。

## 7. 新增规则

### Rule 72 — 「填到哪里」和「填不填得进」是两个独立问题 ★
本项目长期在"填到哪里"上打转(H1/H2/F3 四层回退、filename 污染争议),
但控件清单证明**地址栏根本没有 UIA 元素**,填入方式唯一(Ctrl+L)。
真正的问题是前台锁导致填不进去。
**规则:先用控件清单穷举目标控件,确认哪些可写、哪些不可写,再讨论策略。**

### Rule 73 — 成功的定义必须包含用户可感知 ★
`H1 succeeded` = SendInput 被系统接受,≠ 用户看到对话框跳转。
**规则:任何以「操作已派发」为名的返回值,都不能作为功能验收标准。**

### Rule 74 — 已有代码优先于方案假设 ★
我连续两版方案把 `SetForegroundWindow` 当成"待新增",而它早在 `uia_inject.rs:263` 就存在。
**规则:提"新增某能力"之前,先 grep 确认它是否已存在 —— 缺的往往不是能力,而是配套。**

### Rule 75 — 读产品的既有规则原文,不要读自己的转述 ★
我把 Rule 47 理解成「不要自动完成导航」,于是认为 H1「故意停在半路」。
原文是 **不要自动 Save**。导航与保存是两件事,Enter 只做导航。
**规则:引用一条规则前,回到它的原文与提出时的上下文,不要用自己上一次的转述。**

### Rule 76 — 工具失效时,null 结果不是证据 ★
我试图用二进制字符串扫描判断 Edge 是否还有 `legacy-file-picker` flag。
对照探针显示:14 个真实存在的 flag 里有 7 个同样扫不到 ⇒ **方法有 50% 假阴性**。
**规则**:任何"查不到 / 没找到"的结论,必须先证明查找方法能查到已知存在的目标。
方法未验证时,只能报告"不可知",不能报告"不存在"。
