## 2. 我犯的错误(本次复盘最有价值的部分)

### 错误 1 —— 用错的工具读数据,得出假根因

**症状**:断言「中文路径 mojibake,根因是 UTF-8/GBK 编码错乱」,并写了一整套 Phase 1–3 分析。

**真相**:PowerShell 5.1 默认按 ANSI(936/GBK)解码,而 `spike.log` 是 UTF-8。**我看到的是自己终端的乱码,不是程序的乱码。**

**更糟的一步**:我用这份假数据去「验证」一个 GBK 往返检测算法,算法完美工作,于是我「确认」了根因 —— **我在用自己的错误验证自己。**

**代价**:一整套分析作废,用户多绕一轮。

### 错误 2 —— 把「异常值」当成结论

**症状**:看到日志里 `current=HWND(0x0)`,断定「H1 被永久禁用」。

**真相**:统计全量日志后发现 `H1 succeeded = 48`、`failed = 8`。**我一直死盯着那个 0,忽略了 48 次成功这个更大的样本。**

### 错误 3 —— 补丁静默失败,而我当它成功了

**症状**:用 `$t.Replace('...// v0.5.7 G-2: Update last_known_path', ...)` 插入 `wrote_back = true;`。**锚点注释和文件里的实际文本不一致,Replace 什么也没做,而我没有校验 `Contains`。**

结果:编译通过、66 个测试全绿、功能完全没修好 —— 去重键永远不被更新,resync 每 1.2 秒无限循环。

**同一个错误当天犯了两次**(另一次是插入 `wrote_back` 的锚点)。

### 错误 4 —— 单元测试测不到没被测的层

我的测试全在 `state.rs` 的纯函数上。**没有一个测试覆盖 `main.rs` 的事件处理控制流** —— 而 bug 恰好就在那里。

**我验证了自己的代码,却没验证 API 在它实际被调用位置的行为。** 同一个错误当天犯了三次。

### 错误 5 —— 该先枚举现场,我却先推理

面对「路径填不进弹窗」,我花了五轮分析触发路径和错误码。**而正确答案在 1189 次 UIA 控件观测里:清单中根本不存在地址栏元素。**

**一条朴素的规则,本该在第 1 轮执行:先枚举现场,再分析。**

### 错误 6 —— 同一批操作里部署了未通过门禁的版本

注释里写了 `self-heal` / `Self-healing`,命中沙箱 `/(?<![\w$.])self\b/g`,门禁判定 INVALID。**我修正后重新部署,但同一批操作里已经先部署过一次 INVALID 版** —— 而 Sigma FM 恰好在那次重启,载入被拒绝的 extension,静默失效,一个节点都没跑。

**讽刺的是:这正是 Phase 4 修复的那个失效模式。**

### 错误 7 —— 在用户重启的窗口期里部署

我说「这次我不会在你重启期间部署任何东西」,但我仍然在 Sigma FM 运行期间覆盖了部署文件 —— 而 Sigma FM 只在启动时加载 extension。**覆盖本身安全,但顺序错了。**

## 3. 方法论沉淀

### 规则 72 —— 测量工具必须先自证 ★★★

判定任何数据之前,先证明**读取方式**能正确读出已知正确的样本。

- 本次两次踩坑:ANSI 解码(假 mojibake)、`instanceof Uint8Array` 跨 realm 失效。
- 第二次还做了对照实验:14 个真实 flag 中 7 个扫不到 ⇒ 方法有 50% 假阴性 ⇒ 只能报「不可知」,不能报「不存在」。

**落地**:所有文本读取显式指定 UTF-8;HTTP 响应先取 bytes 再显式解码;任何「查不到」的结论必须先过对照探针。

### 规则 73 —— 修改必须验证生效 ★★★

```powershell
# 错误
$t = $t.Replace($anchor, $replacement)      # 锚点不匹配 = 静默 no-op
# 正确
if (-not $t.Contains($anchor)) { throw "anchor missing" }
```

**编译通过 ≠ 补丁生效。**脚本化修改后必须回读验证。

### 规则 74 —— 明确「我测了什么 / 我没测什么」 ★★★

测试通过只覆盖被测的层。**本次 66 个测试全绿,而 bug 在一个没有测试覆盖的控制流里。**

每次声称「已验证」时,附带一句「未覆盖:XXX」。

### 规则 75 —— 先枚举现场,再分析 ★★

面对「填不到 / 找不到 / 不生效」类问题,**第一步穷举目标对象**(控件清单、事件源、字段全集),再谈策略。

### 规则 76 —— 全量分布优于最近 N 行 ★★

把任何观测值定性为「异常 / 永久 / 结构性」之前,先统计它在**全部历史**中的分布。

### 规则 77 —— 用户的直接观察优先于 AI 的日志推理 ★★★

「地址栏里有没有出现过路径」—— 用户一句话回答了,我五轮日志推理没回答出来。

**当用户已经在现场时,先问一个具体的、10 秒钟能回答的问题。**

### 规则 78 —— 「操作已派发」不是验收标准 ★★

`H1 succeeded` 只表示 SendInput 被系统接受。真正的验收是**用户看到对话框跳转**。

### 规则 79 —— 长期静默的子系统最危险 ★★★

`parsed` 永远是 `null`,导致告警通道和自愈逻辑**在整个项目周期内从未执行过**,却没有任何症状暴露它。

**一个从不成功也从不被检查的分支,等于不存在。**需要为「本应发生的事」建立断言,而不只是为「正在发生的事」。

### 规则 80 —— 门禁要在部署之前,不是之后 ★★

Phase 4 建的沙箱门禁当天就抓到了我自己引入的违规。但**它拦不住我在它之前的那次部署**。

**顺序:构建 → 门禁 → 部署。门禁必须在部署路径上,而不是旁边。**

## 6. 架构层面的教训

### 6.1 「静默失效」是这个项目最大的敌人

本次三个独立的根因,有两个的共同特征是**静默**:

- sandbox 拒绝 → 不加载,无报错
- `JSON.parse` 失败 → 整块逻辑跳过,无报错
- `last_known_path` 从不更新 → 无限循环,只有日志能看出

**如果系统能以「明确失败」的方式出错,以上三个问题都会在第一次出现时被立刻发现。**

**建议**:给关键路径加「本应发生」的断言与心跳,让沉默本身变成信号。

### 6.2 阶段划分帮了大忙

把「extension 能否加载」「extension 能否推送」「sidecar 能否写入」「用户能否感知」
分成四层独立验证,避免了「看起来通了」的错误结论。

### 6.3 三方协作的价值

Claude 提出的 Rule 58(`SetValue ≠ 导航`)比我原方案深一层;
我提出的「全量分布」与「线程消息泵」Claude 都没覆盖。
**分歧经过两轮互相证伪后收敛,比任一方单独判断更可靠。**
